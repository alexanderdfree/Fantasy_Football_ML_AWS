## Open

### [ACKNOWLEDGED] K features use cross-season rolling windows
- **File:** `src/k/features.py:27`
- **What:** Kicker features group by `["player_id"]` only (no season reset), so rolling windows span across seasons. A kicker's late-season 2024 stats influence early-2025 predictions.
- **Rationale:** Kickers have stable multi-year careers and small per-season sample sizes (~17 games), so cross-season windows provide more signal. Comment above the `grp` assignment records this rationale.
- **Risk:** If a kicker changes teams or role between seasons, stale cross-season features could mislead the model. Likely small impact.

### [LOW] Optuna parallel trials wired but disabled by default
- **File:** `src/tuning/tune_lgbm.py:448` (`study.optimize(n_jobs=args.n_jobs)`), CLI flag definition at `:378`.
- **What:** `--n-jobs` exists (default `1`) and is plumbed into `study.optimize`. The default keeps trials serial — nothing flips it on yet. Optuna's thread-based trial parallelism is safe with the existing SQLite storage at `:432`.
- **Why not flipped:** Needs a wall-clock benchmark on the tuning host to confirm a win, and the value must be coordinated with the LGBM tree-learning `n_jobs=-1` (set on Linux in `src/shared/models.py:_LGBM_N_JOBS`) to avoid oversubscribing a 4-vCPU box. On EC2 g4dn picking `--n-jobs=2` (with LGBM at `-1`) is the obvious starting point; `--n-jobs=-1` will fight the per-trial tree-learning threads.

### [LOW] `_cache` dict grows without eviction
- **File:** `src/serving/app.py:87` (`_cache = {}`)
- **What:** `_get_data()` caches results in a module-level dict (serialized by `_cache_lock` since #31). The cache is never cleared. Not a real problem in practice (server restarts frequently), but worth noting.

### [LOW] `drop_last=True` silently discards training samples
- **File:** `src/shared/training.py:167, 196, 449`
- **What:** Last incomplete batch is dropped in all three DataLoaders (attention, multi-target, history-multi-target). With batch_size=512 (WR) and 32,521 training rows, 121 rows (~0.4%) are never seen. Standard practice, but combined with early stopping means those rows never contribute.

### [LOW] K targets overwrite `fantasy_points` column
- **File:** `src/k/targets.py:31`
- **What:** `df["fantasy_points"] = df["fg_yard_points"] + df["pat_points"] - df["fg_misses"] - df["xp_misses"]` overwrites the original column. Safe if called once, but calling twice would use the already-computed value. Not a current bug, just fragile.

### [LOW] Redundant NaN handling in feature engineering
- **Files:** All `*_features.py` files
- **What:** Pattern like `(a / b).fillna(0)` followed by `df.loc[b == 0, col] = 0` is redundant — fillna already handled the division-by-zero case. Not wrong, just noisy.

### [UNCERTAIN] K/DST index collision in `_get_data()`
- **File:** `src/serving/app.py:1079-1092`
- **What:** K/DST test rows are appended to `results` with `offset = results.index.max() + 1`. Assumes the general test data has a well-behaved index. If the general test parquet has gaps, K/DST indices could collide. Probably safe in practice since parquet preserves sequential indices.

### [UNCERTAIN] Team share features computed per-split
- **Files:** `src/rb/features.py:74`, `src/wr/features.py:58`, `src/te/features.py:51`
- **What:** Team carry/target shares are computed within each split independently (`compute_team_*_totals` runs on each split's own data). A player's share could differ between train and test if their teammates are distributed differently across splits. By design (prevents leakage), but the share values won't be globally consistent.

### [FIXED] `ecs_refresh_sentinel` belt-and-suspenders removed after in-flight refresh proven live across 3 retrain cycles
- **File(s):** [.github/workflows/train-batch.yml](.github/workflows/train-batch.yml) (deleted `Kick off ECS rolling deploy (non-blocking)` step + `ecs_refresh_sentinel` job — 68 lines removed), [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) (D14 body past-tensed at line 503 + new 2026-05-21 Update history entry).
- **What:** PR [#302](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/302) shipped the in-flight per-position model refresh (gunicorn `on_starting` daemon polls `models/{POS}/manifest.json` etags every 30 s and atomic-swap-rename the on-disk `models/` dir). train-batch.yml kept the prior delivery path — an `aws ecs update-service --force-new-deployment` kick after benchmark commit, plus an `ecs_refresh_sentinel` `services-stable` wait job — as belt-and-suspenders. The D14 ADR's planned retirement criterion was "remove after the in-flight path runs cleanly for ~2 retrain cycles."
- **Fix:** Verified on 2026-05-21 across 3 retrain cycles (runs #80/#81/#82, all SHA `9409e7e` triggered by the rapid 3-burst of `chore(ci): append Batch benchmark run` commits). CloudWatch `aws logs filter-log-events --log-group-name /ecs/fantasy-predictor --filter-pattern 'swapped to new manifest'` returned 36 events across the two long-running serving tasks (`3c32e6fb` + `9bfef166`). Timeline: first in-flight swap (K, 16:08:41Z) preceded the ECS update-service kick (16:11:24Z) by ~2 min 43 s; the entire six-position fan-out was live on both running tasks by 16:11:24Z; ECS rolling deploy spun up a new task (`ccfcb589`, 16:13:43Z) that bootstrap-loaded the post-train manifest etags directly (zero swap events needed); `ecs_refresh_sentinel`'s `services-stable` returned at 16:19:59Z — ~9 min after the in-flight had finished delivery. Filter for `?"did_refresh=False" ?"refresh failed" ?"falling back to current" ?"falling back to previous"` returned zero matches in the extended window — no fail-soft fallbacks observed across the 36 swaps. Bonus: the in-flight refresh actively recovered task `3c32e6fb` from a degraded RB state (NaN'd ridge/nn/lgbm/attn_nn predictions due to feature-count drift inherited from the prior deploy's stale RB scaler) when the new RB manifest landed at 16:09:42Z — concrete evidence that the in-flight path handles the exact failure mode the sentinel was guarding. Removal deletes only the workflow-level belt-and-suspenders; the per-container `src/{pos}/outputs/.refreshed_at` sentinel file (read by `_ensure_position_loaded` to detect on-disk swaps) and the in-flight poller (`src/shared/model_sync.py::start_refresh_poller`) are unaffected — they remain load-bearing. [.github/workflows/train-ec2.yml](.github/workflows/train-ec2.yml) keeps its ECS kick: it's the `BATCH_ACTIVE=false` rollback path and the conservative posture there is intentional.
- **Lesson:** The "kept as belt-and-suspenders for ~2 retrain cycles" pattern is the right shape for shipping risky-but-better delivery mechanisms: ship the new path live behind the old one, prove the new path in production logs, then remove the fallback. The criterion for retirement is **evidence in the right place** — workflow status alone cannot distinguish "in-flight worked" from "ECS rolling deploy worked"; only serving-side CloudWatch logs can. **Structural rule:** when designing a retirement criterion for a fallback, require the verification signal to be the actual mechanism firing (here: `[refresh] {POS} swapped to new manifest etag=... source=stable` log lines on the serving container), not a downstream proxy (workflow `services-stable` succeeding doesn't prove the in-flight path actually did anything). Companion lesson on naming-collision: `ecs_refresh_sentinel` (the workflow job) and `.refreshed_at` (the per-container file) share the word "sentinel" but solve different problems — the file is the request-path detection mechanism for the in-flight swap; the job was the workflow-level confirmation that ECS rolling deploy converged. Sole-mechanism removal targets the *workflow* artifact; touching the file would have broken the in-flight path the sentinel job was protecting.

### [FIXED] `/health` returned 503 on partial per-model failure → ECS killed serving tasks (single-task service had no redundancy)
- **File(s):** [src/serving/app.py](src/serving/app.py) (`_apply_position_models` — new stale-error clear before per-model loaders; `/health` — rewritten to return 503 only when `positions_loaded` is empty, 200+`status="degraded"` when partial errors but at least one position serves), [tests/test_app_apply_position_models.py](tests/test_app_apply_position_models.py) (existing `test_health_route_degraded_when_load_errors_present` rewritten + 2 new `/health` tests + 1 new `_apply_position_models` clear-stale-errors test). Operational changes (no code): `aws ecs update-service` on `fantasy-cluster/fantasy-service` set `desiredCount=2` and `deploymentConfiguration.deploymentCircuitBreaker={enable=true,rollback=true}`.
- **What:** On 2026-05-21 12:16:37 UTC, `alexfree.me` returned 503 to ~14 requests over ~62 s. CloudWatch `HTTPCode_ELB_5XX_Count` confirmed the burst; ECS service events showed the single running task (`6bebb206…`) self-reported 503 on `/health` and was killed by ALB (`unhealthy_threshold=3 × interval=10s` ⇒ ~30 s), leaving 0 healthy targets until the replacement task passed HC. Three factors stacked: (1) `desiredCount=1` — no redundancy on any single-task failure; (2) `_apply_position_models` (in [src/serving/app.py](src/serving/app.py)) writes per-model failures under `position_load_errors["{pos}_{model_type}"]` keys (e.g. `"QB_ridge"`), but the in-flight refresh's clear at `_ensure_position_loaded` only popped the bare `pos` key — per-model entries latched forever once written; (3) `/health` returned 503 for *any* non-empty `position_load_errors` map, which on a transient S3 model-refresh failure (PR [#302](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/302)'s in-flight refresh poller path) flagged the entire task as unhealthy even though five of six positions were still serving cleanly. `/api/predictions` was already returning 200 + a `degraded_positions` banner for the exact same state (test in [tests/test_app_degraded_mode.py::test_inner_per_model_failure_records_without_raising](tests/test_app_degraded_mode.py)) — so `/health` was *stricter* than the actual user-facing serving contract, and that mismatch is what killed the task.
- **Fix:** Three layers, ordered by impact. **(A) HA: `desiredCount=2`** via `aws ecs update-service --desired-count 2` on the live service. Subnets already span two AZs, so the second task lands in a different AZ. With `minimumHealthyPercent=100` + `maximumPercent=200` (unchanged), ECS now guarantees ≥2 healthy throughout any rolling deploy; any single-task self-failure no longer drops the site. Cost delta: ~$72/month for the second 2 vCPU + 4 GB Fargate task. **(B) `/health` self-heal** in [src/serving/app.py](src/serving/app.py): `_apply_position_models` now drops every `{pos}` and `{pos}_*` entry from `position_load_errors` before re-loading (matches the key-parsing rule in `_degraded_positions`), so a successful refresh actually clears the latch. **(C) `/health` contract change** in [src/serving/app.py](src/serving/app.py): returns 503 only when we have **affirmatively** failed — `position_load_errors` is non-empty AND `positions_loaded` is empty (every load attempt failed). Returns 200 + `status="degraded"` + the full `position_load_errors` map + the `positions_loaded` list when at least one position is loaded but there are recorded errors. Returns 200 + `status="ok"` for cold start (both maps empty — task is alive, `post_fork` pre-warm thread is still running) and steady state (every position loaded, no errors). The "errors AND nothing loaded" predicate distinguishes "haven't tried yet" from "tried and failed" — a naive "503 when nothing loaded" would 503 the ~30 s pre-warm window and ALB (`interval=10s × unhealthy_threshold=3`) would deregister every fresh task before warmup completes. Aligns with `/api/predictions`'s "any position serving = we're up" contract. **(D) Defense in depth: ECS deployment circuit breaker** via `aws ecs update-service --deployment-configuration "deploymentCircuitBreaker={enable=true,rollback=true},..."` — broken deploys auto-rollback to the prior task definition instead of waiting the full `wait-for-minutes: 20` in [.github/workflows/deploy.yml](.github/workflows/deploy.yml). Verified end-to-end: 5 consecutive `curl https://alexfree.me/` probes returned 200, ALB target group reports 2 healthy targets, ECS `runningCount=desiredCount=2`, `rolloutState=COMPLETED`. The existing inflight-refresh determinism test [tests/test_app_inflight_refresh.py::test_refresh_clears_failed_state_and_retries](tests/test_app_inflight_refresh.py) still passes — it tests the bare-`pos` key path, which (A)/(B)/(C) didn't change. New [tests/test_app_apply_position_models.py::test_apply_position_models_clears_stale_errors_for_this_position](tests/test_app_apply_position_models.py) pins the `{pos}_{model_type}` clear-on-reload behaviour; new `/health` tests pin the three return shapes (`ok`, `degraded`+200, `unhealthy`+503).
- **Lesson:** When two endpoints describe the same operational state but use different status codes, the *stricter* one becomes the de facto health contract — and if the stricter one is wrong, the looser one is fiction. `/api/predictions` returning 200 + `degraded_positions` was the *correct* user-facing serving contract ("partial degradation is still serving"); `/health` returning 503 on any per-model error was a stricter contradiction that nobody noticed until it killed a task. **Structural rule:** when designing a degraded-mode response shape, the same predicate ("is the task usefully serving?") should drive every operator-facing signal — health probe, structured-response status field, frontend banner — or one of them is going to be the load-bearing one that triggers ECS replacement. Companion infra lesson: `desiredCount=1` on a serving service is a single point of failure that no amount of code resilience can paper over — even a perfectly-coded task can be killed by a transient ALB-layer event (e.g. an unhealthy-threshold trip during a slow GC), and the only way to bridge that window is having a second target healthy. Pair the multi-task baseline with deployment circuit breaker + rollback for the *deploy* class of failures (broken image, broken `/health` contract change), and the two together cover most of the "ECS dropped me" class of incidents. Cross-link: the in-flight S3 model-refresh poller introduced by PR [#302](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/302) is what *populates* `position_load_errors` mid-flight on transient S3 errors — the poller itself is correct (best-effort refresh that records and continues), but its consumer (`/health`) was over-eager about treating the error map as "broken task" rather than "broken model artifact, the rest still works."

### [FIXED] `_GPUResidentBatcher` drew permutations from CUDA RNG, diverging the per-epoch batch order from the CPU/MPS DataLoader path
- **Files:** [src/shared/training.py](src/shared/training.py) (one-line fix in `_GPUResidentBatcher.__iter__`: `torch.randperm(self._n, device=self._device)` → `torch.randperm(self._n).to(self._device)`; expanded the surrounding docstring to spell out the CPU/CUDA RNG stream split). No subclass overrides — every position inherits the fix because `_GPUResidentBatcher` is the single class all four `make_*_dataloaders` instantiate on CUDA.
- **What:** PR [#309](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/309) (`04ef622`) introduced `_GPUResidentBatcher` to replace the CUDA-side `DataLoader` path. Its `__iter__` generated the per-epoch permutation via `torch.randperm(self._n, device=self._device)` (i.e. on the CUDA device). The docstring claimed this matched "DataLoader's default RandomSampler when constructed with `generator=None`" — false. PyTorch maintains *independent* default generators per device: `torch.default_generator` (CPU) and `torch.cuda.default_generators[i]` (CUDA). `seed_everything(42)` in [src/shared/utils.py](src/shared/utils.py) seeds both via `torch.manual_seed(42)` + `torch.cuda.manual_seed_all(42)`, but they're separate streams that produce different sequences at the same numeric seed. The old `DataLoader(shuffle=True)` consumed the CPU stream (via `RandomSampler`); the new `_GPUResidentBatcher` switched to the CUDA stream silently. Same seed, different batch order per epoch on CUDA hosts → a real divergence in the SGD trajectory vs the CPU/MPS path (and vs every pre-PR-#309 production run, which had used DataLoader on CUDA). The bug was universal across all 6 positions — every one of them generates fresh permutations through this single code path. The bug only became *visible* as a QB MAE regression in the PR #307 production-validation run (2026-05-21 ~11:24 UTC, 6 successful jobs against image `04ef622`): QB attn_nn aggregate +2.68% vs FP32 baseline `00c6d10`, driven by `passing_yards` head +4.50% (68.35 → 71.43 yds). DST went the *other* way (attn_nn aggregate -3.42%, `yards_allowed` -4.70%) — same batch-order drift, but DST's loss surface lucked into a better local minimum at the new ordering. Other positions moved in noise. The variance across positions is what makes "per-position fallback" the wrong framing — the bug is one bug, the impact distribution is a function of per-position loss-surface sensitivity to batch ordering, with `passing_yards`'s Huber-δ=15 / ~250 yds/game magnitude making QB the loudest signal.
- **Fix:** `torch.randperm(self._n)` defaults to `device='cpu'` and consumes `torch.default_generator` — the CPU stream that `seed_everything()` seeds and that `DataLoader(shuffle=True)`'s `RandomSampler` also reads from. `.to(self._device)` ships the resulting int64 permutation tensor to the GPU. For N≈20k that's a ~160 KB single H2D copy / ~50 μs per epoch — negligible vs the ~100s of NN forward/backward per epoch, and many orders of magnitude smaller than the DataLoader IPC + per-batch H2D copy that PR #309 removed. Not *bit-identical* to the old DataLoader's `RandomSampler.__iter__` (which constructs a transient `torch.Generator` per epoch and consumes one int64 from the global RNG as the seed for its `torch.randperm` call), but the contract — "draw from CPU global RNG so the same seed maps to the same batch order across CPU/MPS/CUDA hosts" — now holds. `tests/test_reproducibility.py` (3 parametrized tests × 6 positions = 18 cases) re-validates the byte-identical-state_dict contract on CPU (where this code path isn't reached); all 18 passed locally. The CUDA-side validation will be the next post-merge `train-batch.yml` run. The fix does not necessarily fully recover the 00c6d10 baseline — PR [#301](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/301)'s FP16 autocast is a *separate* numerical-drift source for QB that was deliberately deferred (handled per-position with `nn_use_amp=False` if needed in a follow-up). **Update 2026-05-21 (post-#313 train-batch validation run):** QB attn_nn aggregate came back within tolerance of the 00c6d10 FP32 baseline on the RNG fix alone. The deferred AMP follow-up is **retired** — no per-position `nn_use_amp=False` is needed for QB.
- **Lesson:** Docstring contract violations are silent corruption when the underlying mechanism is a global. The PR #309 author's intent was "use the CPU global RNG so the GPU-resident path is interchangeable with the DataLoader fallback" — and the comment said as much — but the code did the opposite. `torch.randperm(n, device='cuda')` works syntactically (no error, no warning), runs to completion, returns a deterministic permutation at a CUDA-seeded state, and silently shifts the SGD trajectory away from every preceding run. **Two structural rules to lift**: (1) When PyTorch exposes "per-device default generators" (CPU + CUDA, separate streams), any tensor-allocating randomness primitive whose API takes a `device` argument has a hidden RNG-stream switch. If the intent is "reproduce on the same numerical seed across devices," the safe pattern is `torch.randperm(n)` on CPU then `.to(device)` — *not* `torch.randperm(n, device=…)`. Same applies to `torch.randn`, `torch.randint`, etc. (2) When a refactor swaps a stable, well-known PyTorch utility (`DataLoader(shuffle=True)`) for a hand-rolled equivalent (`_GPUResidentBatcher`), the docstring's claim of "same as the utility" should be backed by a determinism unit test that exercises both paths under the same global seed and compares the first epoch's batch indices. The reproducibility tests in [tests/test_reproducibility.py](tests/test_reproducibility.py) test SAME-DEVICE reproducibility (good for catching dtype/op drift) but don't compare the GPU-resident path against the DataLoader path. Adding that cross-path determinism test would have caught this on PR #309's CI gate before the regression shipped — captured separately as a follow-up. Cross-link: this is the second-order regression downstream of [the BLAS thread cap entry](#fixed-blas-thread-oversubscription-hung-sklearn-ridge_tune-on-t4-after-pr-301-unmasked-the-parallel-cpu-branch) below (PR #307) — unblocking the GPU branch is what exposed the GPU-resident batcher's behavior under real load + a benchmarkable baseline. The PR #301 FP16 contribution to QB's residual drift was captured separately as a follow-up; **retired** when the post-#313 production-validation run brought QB back within tolerance on the RNG fix alone.

(2) **Dedup early-exit** via a new `dedup_check` job (parallel with `detect`, so total overhead is `max(detect, dedup_check) ≈ 1 min`, not `detect + dedup_check`): under `workflow_run`, query `gh run list --workflow=train-batch.yml --status=success --head-sha <SHA>` excluding the current run; if any prior success exists, set `skip=true`; `train` job's `if:` reads that output and short-circuits. Under `workflow_dispatch`, `dedup_check` bypasses (manual dispatches are operator-driven and always run). Net effect: same-SHA duplicates now spend ~1 min on detect + dedup-API-call → train-skip, instead of ~15 min on full detect → checkout → install → submit → wait → benchmark-append → ECS-refresh. The concurrency layer also bounds wall-clock: a 3rd or 4th queued duplicate doesn't run in parallel, it waits for the prior to finish — by which time the prior is in either `success` (dedup short-circuits) or `failure` (dedup proceeds, useful as a retry). The two-layer design is necessary because either layer alone has a gap: concurrency alone still spends full CI on the queued run; dedup alone races (two parallel runs would both see "no prior success" and both run).
- **Lesson:** GitHub Actions workflow_run delivery is at-least-once, not exactly-once — any downstream workflow that fans out into expensive work on `workflow_run.completed` should serialize same-SHA fires *and* dedup mid-run, not just one or the other. Companion lesson on debugging the hypothesis: the user's initial "operator manually re-ran batch-image.yml" theory matched the symptom (duplicate downstream fires) but contradicted the data (`run_attempt: 1` everywhere). Confirming root cause via the API field that *would* differentiate the hypothesized cause (manual rerun → `run_attempt > 1`) from the actual cause (GitHub multi-delivery → `run_attempt == 1`) was the critical step — without that field check, the "fix" might have been a more elaborate version of "tell operators to stop manually retrying batch-image" which would have done nothing. Companion lesson on concurrency-group keys: keying by `github.run_id` would serialize ALL train-batch runs into one queue (bad — kills cross-PR Spot fan-out); keying by `github.event.workflow_run.id` would let duplicates from the same upstream still run in parallel (bad — that's exactly what we're trying to prevent); keying by `head_sha` is the right granularity. Cross-PR parallelism + same-SHA dedup, expressed in one group-key expression.

### [FIXED] Gunicorn `--preload` pre-warm broke ALB health checks during task replacement
- **Files:** gunicorn launch config / Dockerfile CMD. Tried in PR #148 (`d69f427`), reverted in PR #149 (`8ff26be`).

- **Files:** `.github/workflows/deploy.yml:76-99` (rewritten to use `aws-actions/amazon-ecs-render-task-definition@v1` + `amazon-ecs-deploy-task-definition@v2` with `wait-for-minutes: 20`), `infra/aws/bootstrap.sh:318` (+`--availability-zone-rebalancing DISABLED` on create-service).

### [FIXED] Softplus floor inflated low-scoring predictions (twice)
- **Files:** `src/shared/neural_net.py:106, :407, :589` (all three `MultiHeadNet*` variants)
- **What:** `softplus(0) ~ 0.693` per head creates a floor that compounds across heads: ~2.08 pts for a 3-head position, ~2.8 pts for K's 4-head sum, etc. No player could be predicted below the floor. Also created a scale mismatch with Ridge (`np.maximum(..., 0)` allows exact zeros), biasing the ensemble.
- **First fix:** Replaced with `torch.clamp(val, min=0.0)` so heads can emit exact zeros.
- **Regression:** Commit `845d93b` reverted the clamp back to `F.softplus` at lines 106 and 407 and extended the softplus floor into the new `MultiHeadNetWithNestedHistory` at line 589 (so K inherited the bug). Also dropped a separate `torch.clamp(td_pred, min=0.0)` around GatedTDHead's output — left unchanged this time because GatedTDHead's `sigmoid × softplus(value)` is already in `[0, +∞)` and doesn't need an outer clamp.
- **Re-fix:** Restored `torch.clamp(val, min=0.0)` at all three sites.
- **Lesson:** Non-negativity constraints on output layers must allow exact zeros. Softplus is good in hidden layers (smooth gradient), but on outputs its floor compounds across heads. When porting a new model variant, re-check which output transforms the existing variants use — don't copy the pre-fix pattern. Consider a shared `_apply_non_negative` helper so a future reviewer can't silently diverge one variant.
