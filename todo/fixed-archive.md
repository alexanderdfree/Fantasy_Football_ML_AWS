### [FIXED] refresh-splits.yml verify-before-publish ordering → train-batch fail-safe trained on STALE splits
- **File(s):** [../.github/workflows/refresh-splits.yml](../.github/workflows/refresh-splits.yml) (step order); guarded by [../tests/test_refresh_splits_workflow.py](../tests/test_refresh_splits_workflow.py).
- **What:** refresh-splits ran two slow **warn-only diagnostics** — "Verify train→test covariate shift" + "Verify depth-chart temporal alignment" — BEFORE "Upload to S3" + "Mark splits-rebuild ready". On a cold-cache run the ~14.5-min regen + the ~15-min covariate diagnostic pushed the ready marker past train-batch's ~20-min fail-safe wait, so train-batch proceeded on the EXISTING (stale) S3 splits and CANCELLED the orphaned refresh-splits — the freshly-built splits were never published. Silent: the refresh run shows `cancelled`, the splits actually regenerated fine (step 8 ✓), and the model just trains a commit behind. First caught on the #1051 (`4b76fb2`) retrain. Would also mask any Tier-C split-build metric-mover as a **false Δ0**.

Marker now lands ~1 min after regen+upload, well inside the fail-safe window. Column-presence gate still precedes the upload (8c46b59 protection intact); ready-after-upload + ECS-after-upload invariants preserved (all 9 workflow tests pass).

### [FIXED] CUDA-graph capture fired on CPU-device trainers (FF_CUDA_GRAPH) → NaN / flaky NN tests on a GPU dev box
- **File(s):** [../src/shared/training.py](../src/shared/training.py) (`MultiHeadTrainer._maybe_graph_model` guard, ~L776). Symptom surfaced in `tests/k/test_training.py::TestMultiHeadTrainer::test_losses_decrease` and `tests/k/test_regression.py::test_nn_within_25pct_of_lightgbm` (and the same `device=cpu` trainer pattern in every position's `test_training.py`/`test_regression.py`).
- **What:** `_maybe_graph_model` gated capture on **only** the global capability check `cuda_graph_enabled()` (autodetect-ON for any sm_80+ host — the RTX 5080 is sm_120) and never on the trainer's *own* `self.device`. Many unit/integration tests (and any `FF_DEVICE=cpu` run on a GPU box) construct `MultiHeadTrainer(..., device=torch.device("cpu"))`. On a CUDA host those CPU-device trainers still entered the guard and called `torch.cuda.make_graphed_callables` on a **CPU** model → captured garbage → `NaN` MAE ("no valid checkpoint saved (all epochs had NaN MAE)") / non-decreasing train loss. Green on CPU/CI (where `cuda_graph_enabled()` is False) and in single-process local runs, red under the default `-n auto` GPU run → read as a "K NN test flake" (#690, which had been triaged `leave` as "K's nested trainer no-ops capture" — that closed the K *crash* but not this base-trainer flake). The base `MultiHeadTrainer` was the actual culprit, so it hit all six positions, not just K.
- **Fix:** Added `self.device.type != "cuda"` to the early-return: `if self._graphed or self.device.type != "cuda" or not cuda_graph_enabled(): return`. Mirrors the two existing per-trainer device gates — the AMP gate in `__init__` (`getattr(device, "type", None) == "cuda"`, ~L652) and the `_cuda` guard in `train()` (~L837). **Numerically inert on production:** Batch trains on CUDA (g6/L4 sm_89) where `self.device.type == "cuda"`, so the new clause is False and control flow is byte-identical → no benchmark move, no graphed-vs-graphed rebaseline. Verified: K NN tests 47 passed ×3 under xdist (was 2 failed ×3); `tests/shared/test_cuda_graph.py` 28 passed (real capture still exercised); `pytest -m unit` 2535 passed on the 5080.
- **Lesson:** A *global* capability check (`cuda_graph_enabled()`, `amp_dtype()`, `_gpu_resident_device()`) is not the same as the *caller's intended device*. Anything that engages a CUDA-only fast path must also confirm the consumer is actually on CUDA — the trainer knows its `self.device`; use it. **Related (separate mechanism, fixed in the follow-up entry below):** `make_dataloaders` / `make_history_dataloaders` make the *same* mistake via `_gpu_resident_device()` — a CPU-device trainer on a GPU box gets GPU-resident, non-bit-identical, unseeded-shuffle loaders, which flakes the `@pytest.mark.integration` regression tests (qb/rb/wr/dst: NN MAE 60–100 vs LGBM 5–15, varying run-to-run; passes with `FF_DEVICE=cpu`). That path is graph-independent (reproduces with `FF_CUDA_GRAPH=0`), CI-safe (CPU), and was *not* fixed in this PR — the dataloader factory doesn't receive the device. Fixed in the follow-up by making residency opt-in (see next entry).

### [FIXED] GPU-resident dataloaders engaged on CPU-device trainers → flaky @integration regression tests on a GPU box
- **File(s):** [../src/shared/training.py](../src/shared/training.py) (`_gpu_resident_device` + the four `make_*_dataloaders` factories) and [../src/shared/pipeline.py](../src/shared/pipeline.py) (5 factory call sites). The follow-up to the CUDA-graph device-gate fix above.
- **What:** `make_dataloaders` / `make_history_dataloaders` / `make_history_with_opp_dataloaders` / `make_nested_kick_dataloaders` chose the GPU-resident batcher (`_GPUResidentBatcher`) via `_gpu_resident_device()`, which keyed off the **global** `cuda_enabled()` — not the device the trainer would actually run on. On a GPU box the per-position `@pytest.mark.integration` regression/threshold tests build `MultiHeadTrainer(..., device=torch.device("cpu"))` but called the factories with no device, so they received GPU-resident loaders whose shuffle both differs from the CPU `DataLoader` path and isn't seeded the same way → the tiny synthetic-data NN converged to wildly different minima (qb/rb/wr/dst NN MAE 60–100 vs LGBM 5–15), varying run-to-run. Green on CPU/CI; flaky only on a CUDA-visible dev box. Graph-independent (reproduced with `FF_CUDA_GRAPH=0`); `FF_DEVICE=cpu` masked it (it forces `_gpu_resident_device()`→None).
- **Fix:** Made GPU residency **opt-in by the caller's training device**. `_gpu_resident_device(device)` now returns the resident device only when the passed `device` is CUDA; the four factories take an optional `device=None` (default → plain `DataLoader`); `src/shared/pipeline.py` passes the resolved `_nn_device()` at all five call sites. **Numerically inert on production:** on a GPU host `_nn_device()` is `cuda`, so residency engages with the *same* device as before (byte-identical; e2e pipeline tests pass on GPU). Tests / CPU callers default to `device=None` → the deterministic CPU loader → CI-faithful local runs. Verified on the 5080: all-position regression+training 131 passed ×2 under `-n 8` (was 6 failed), `pytest -m unit` 2536 passed.
- **Lesson:** Same root lesson as the entry above, second instance: a factory that engages a CUDA fast path must learn the *consumer's* device, not sniff global CUDA availability. When the factory runs before the trainer exists (so it can't read `self.device`), thread the intended device in and default residency OFF — production opts in explicitly, tests/CPU stay deterministic. Flipping the default to opt-in fixed every call site with **zero per-test edits** (only the 5 production call sites + the factory signatures changed), not the ~50 test-site churn a default-autodetect-plus-opt-out approach would have needed.

### [REMOVED] SOCI lazy-loading never worked on AWS Batch (ECS-EC2 unsupported)
- **File(s):** [../infra/batch/userdata.sh](../infra/batch/userdata.sh) (deleted), [../infra/batch/setup.sh](../infra/batch/setup.sh) (launch-template machinery removed; the `instanceTypes` reconcile from the adjacent g4dn→g6 fix is preserved), [../.github/workflows/batch-image.yml](../.github/workflows/batch-image.yml) ("Publish SOCI index" step removed), [../docs/batch_design.md](../docs/batch_design.md) §2a + [../infra/batch/README.md](../infra/batch/README.md) (claims corrected). Investigated/validated on live AL2023 ECS GPU hosts (containerd 2.2.1), 2026-06-07.
- **What:** The Batch cold-start optimization claimed SOCI lazy-loading cut the image pull ~122s → ~5–10s (total cold-start ~258s → ~135s). It **never fired**: live ECS task pull windows measured ~118–122s. Two layers of failure: (1) `userdata.sh` only registered the `[proxy_plugins.soci]` proxy plugin but never *selected* soci as the snapshotter (containerd 2.x **transfer-service** `unpack_config`), gave the daemon **no ECR credentials**, or enabled the `soci_v1` pull mode; (2) more fundamentally, AWS Batch runs on **ECS-managed EC2**, and the **amazon-ecs-agent does not pull through the soci snapshotter** — SOCI on ECS is **Fargate-only** ([aws/containers-roadmap#1832](https://github.com/aws/containers-roadmap/issues/1832), open since 2022). Fargate has no GPU, so GPU training (→ must be EC2 → ECS agent) can never use it — and this is the ECS agent's limitation, **not** the GPU arch, so the just-completed g4dn→g6 migration (adjacent entry) does **not** unblock it.
- **Evidence:** Fixed all three userdata gaps and *validated lazy-load works for a `ctr` pull* on a fresh AL2023 host (7s / 9 KiB transferred / 8 FUSE mounts / `remote-snapshot-prepared:true`). But a prod K smoke test on a (g4dn-at-the-time) host with that exact config still pulled in **103s** (overlayfs) — the ECS agent ignored the snapshotter config. The ECR index is fine (referrers API returns it, subject = image digest) and the job def correctly pins the indexed `:$sha`; the gap is purely the ECS-agent pull path.
- **Fix:** Removed the SOCI machinery (userdata launch template, CI index publish, `setup.sh` LT plumbing). Cold-start returns to the ~120s full pull it always actually was (no regression — the SOCI path was inert). Mid-investigation, an attempted LT detach also surfaced a footgun: the README's documented `launchTemplate={}` detach is rejected by AWS, and chaining a `delete-launch-template` past that failed gate left the CE pointing at a deleted template — recovered by recreating `ff-batch-lt` as a no-op (AWS Batch can't drop a launch-template *reference* from an existing CE without recreating it). Cold-start levers that DO work on GPU/EC2: a **warm pre-pulled instance** (no pull at all) or shrinking the 3.8 GB image.
- **Lesson:** SOCI lazy-loading is a **Fargate** feature; the ECS-EC2 `amazon-ecs-agent` does not use the soci snapshotter regardless of containerd config **or GPU arch**. A containerd-level fix that works for `ctr`/CRI does **NOT** imply the ECS agent uses it — verify a cold-start optimization with the **actual ECS task pull window** (`describe-tasks` `pullStartedAt`/`pullStoppedAt`), not a `ctr` proxy. And never chain a destructive `delete` past an unverified `update` gate. Don't re-attempt SOCI on the Batch path unless AWS ships #1832.

- **File(s):** [../infra/batch/setup.sh](../infra/batch/setup.sh) (reconcile branch now diffs + updates `instanceTypes`; `INSTANCE_TYPE` single source of truth), the live `ff-gpu-spot` CE (migrated `g4dn.xlarge`→`g6.xlarge`), and the g6/L4 doc/label re-alignment across [../src/batch/launch.py](../src/batch/launch.py), [../src/batch/benchmark.py](../src/batch/benchmark.py), [../.github/workflows/train-batch.yml](../.github/workflows/train-batch.yml), [../AGENTS.md](../AGENTS.md), [../docs/batch_design.md](../docs/batch_design.md) (revert of #936/bcc1206, now that the migration is real).
- **What:** The 2026-05-31 ADR-0013 g4dn→g6 migration flipped `instanceTypes` in setup.sh's CE-**create** block and instructed operators to run `bash infra/batch/setup.sh` to reconcile the live CE. But the "CE already exists" branch only reconciled the **launch template** — it never read or updated `instanceTypes`. So every re-run was a silent no-op on instance type and the live `ff-gpu-spot` CE kept launching `g4dn.xlarge` (T4, sm_75) for a week. Found 2026-06-07: the live CE was still g4dn (#936/bcc1206 reverted the docs to match reality instead of fixing the migration), which kept CUDA graphs / `torch.compile` / BF16 gated off (sm_75 < sm_80) even though the autodetect was live.
- **Fix:** (1) Migrated the live CE directly: `DISABLE → update-compute-environment --compute-resources instanceTypes=[g6.xlarge] → ENABLE` (minvCpus=0 ⇒ no fleet disruption; confirmed `VALID`/`ComputeEnvironment Healthy`). When extending such a branch, diff **every** field the create block sets. And verify infra against `aws … describe-*`, not the committed IaC — "declared" ≠ "deployed."

### [FIXED] Blocked Chart.js CDN took down the entire serving UI
- **File(s):** [../src/serving/templates/index.html](../src/serving/templates/index.html) (CDN `<script>` → self-hosted), `../src/serving/static/js/vendor/chart.umd.min.js` (vendored Chart.js v4.4.0), [../tests/test_app.py](../tests/test_app.py) (`TestStaticAssets` regression guard).
- **What:** The app loaded Chart.js from `cdn.jsdelivr.net`. `app.js` references the `Chart` global at init, so when the CDN was unreachable (offline / air-gapped / blocked network policy / cert failure) the script tag failed, `Chart` was undefined, and init threw **before binding the tab click handlers** — taking down *all* event wiring, not just the chart tabs. The whole UI went dead (tabs unclickable), not gracefully degraded. Found while browser-verifying PR #886 in a CDN-blocked container.
- **Fix:** Vendored the pinned `chart.umd.min.js@4.4.0` under `src/serving/static/js/vendor/` and repointed the template to `/static/js/vendor/chart.umd.min.js`. No Dockerfile change — `COPY src/ src/` already bundles `static/` into the serving image. Verified with headless Chromium and the CDN hard-blocked: zero jsdelivr requests, `Chart` defined, tabs wired, History + chart tabs render with no `pageerror`.
- **Lesson:** A third-party `<script>` whose global is touched at init is a single point of failure for the *whole* page, not just the feature using it — one failed CDN load throws and unbinds every later listener. Self-host front-end vendor deps (the build already ships `static/`). The script-tag load is a real network boundary, so removing it is warranted (cf. AGENTS.md "Don't add error handling for cases that can't happen" — network boundaries are the exception).

No test change — [tests/shared/test_core_pool.py](tests/shared/test_core_pool.py) already drives the coordinator through the returned `addr`, so the short-path fallback is transparent to it.

The correct detector is the **near-exact fraction**: drop a season if >`_LOOKAHEAD_FRAC` (0.30) of rows land within `_LOOKAHEAD_EPS` (0.5 pt) of the actual — the copied rows pile up at residual≈0 regardless of overall std. Don't trust a provenance caveat's direction; measure. (2) **Detector:** residual std (or any aggregate-spread metric) only catches *fully* copied seasons — **partial backfill hides in a normal std**. The right test for "is this projection secretly the actual?" is the **exact/near-exact match fraction to the realized value**, validated on a genuinely held-out slice. Integer-vs-fractional is a corroborating tell (real projections are fractional expected values). A reviewer's "I don't believe that" is what forced the forensic per-row check that found 2021/2022 too — cheap-proxy diagnostics (std) can be directionally right but quantitatively incomplete.

ADR: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) D4 (2026-05-30).
- **What:** The Part-2 history-depth analysis flagged that at `n_prior_games==0` (season opener; RB n=159) the attention NN over-predicts — bias **+1.13**, MAE 3.81, the worst non-Ridge model (plain NN handles no-history best at 3.26). Root cause: `build_game_history_arrays` groups history by `(player_id, season)` and skips the first game of each, so an opener has an all-padding sequence → `AttentionPool` `-inf`-masks it → softmax NaN → `nan_to_num(0.0)` → **zero pooled vector** → the per-target LayerNorm maps zero to its constant bias → the head leans entirely on the static prior-season branch, which runs hot. The model had only weak indirect signal (`week`) that there is no in-season history.
- **Fix:** A per-target **learned** embedding replaces the dead/constant vector for empty-history rows, gated on the all-False mask. Zero-initialised and constructed last so it draws no RNG and is bit-identical to the baseline at init — making the flag OFF/ON A/B exactly ceteris-paribus (deterministic Ridge/NN/LGBM MAE identical to 6 d.p., confirming the delta is the embedding, not RNG). Enabled on all five flat-attention positions (QB/RB/WR/TE/DST; K's nested path excluded). Real-pipeline result: RB opener bias +1.13→+0.52, opener MAE 3.81→3.39 (seed 42, direction confirmed on a 2nd seed); QB/WR/TE/DST (seed 42) all non-negative — QB opener −0.245 MAE, DST overall −0.065, WR/TE flat-to-mild; no history-depth bucket regresses; overall MAE flat-to-slightly-better.
- **Rejected sub-variant:** mirroring the embedding onto the **opp-defense** history branch. A defense's in-season history is empty iff **week 1**, and every week-1 player is already a season opener, so `opp-empty ⊆ player-empty` (confirmed exactly: 99 week-1 rows ⊂ 159 `npg==0` rows). The opp embedding therefore reaches no row the player embedding doesn't — it only **double-counts** the opener signal: it competes for the same week-1 gradient (diluting the player correction to opener bias +0.86) and adds overfit-prone capacity (RB overall regressed 4.15→4.25). Reverted; the player branch is the sufficient home.
- **Lesson:** (1) Give "missing data" a learned representation only where the missingness carries a **systematic, learnable bias** *and* isn't already encoded — the player-empty case qualifies (static branch over-predicts); the opp-empty case is a strict subset of it, so a second embedding just re-encodes the same week-1 signal (same "one signal, one place" discipline as the no-rolling-in-the-attention-static-channel rule). (2) The baseline opener problem is **seed-sensitive** (RB opener bias +1.13 at seed 42 vs +0.72 at seed 123) — judge by the **direction** across seeds, not the magnitude at one; the headline "overall −0.10 / beats LGBM" was seed-42 luck and did not replicate. (3) Zero-init + construct-last makes an architecture-change A/B bit-identical at init, the cleanest way to attribute a metric delta to the change rather than weight-init RNG. Subgroup slice: `add_history_depth(result["test_df"])` + the `pred_{model}_total` columns.

### [FIXED] `_GPUResidentBatcher` drew permutations from CUDA RNG, diverging the per-epoch batch order from the CPU/MPS DataLoader path
- **Files:** [src/shared/training.py](src/shared/training.py) (one-line fix in `_GPUResidentBatcher.__iter__`: `torch.randperm(self._n, device=self._device)` → `torch.randperm(self._n).to(self._device)`; expanded the surrounding docstring to spell out the CPU/CUDA RNG stream split). No subclass overrides — every position inherits the fix because `_GPUResidentBatcher` is the single class all four `make_*_dataloaders` instantiate on CUDA.
- **What:** PR [#309](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/309) (`04ef622`) introduced `_GPUResidentBatcher` to replace the CUDA-side `DataLoader` path. Its `__iter__` generated the per-epoch permutation via `torch.randperm(self._n, device=self._device)` (i.e. on the CUDA device). The docstring claimed this matched "DataLoader's default RandomSampler when constructed with `generator=None`" — false. PyTorch maintains *independent* default generators per device: `torch.default_generator` (CPU) and `torch.cuda.default_generators[i]` (CUDA). `seed_everything(42)` in [src/shared/utils.py](src/shared/utils.py) seeds both via `torch.manual_seed(42)` + `torch.cuda.manual_seed_all(42)`, but they're separate streams that produce different sequences at the same numeric seed. The old `DataLoader(shuffle=True)` consumed the CPU stream (via `RandomSampler`); the new `_GPUResidentBatcher` switched to the CUDA stream silently. Same seed, different batch order per epoch on CUDA hosts → a real divergence in the SGD trajectory vs the CPU/MPS path (and vs every pre-PR-#309 production run, which had used DataLoader on CUDA). The bug was universal across all 6 positions — every one of them generates fresh permutations through this single code path. The bug only became *visible* as a QB MAE regression in the PR #307 production-validation run (2026-05-21 ~11:24 UTC, 6 successful jobs against image `04ef622`): QB attn_nn aggregate +2.68% vs FP32 baseline `00c6d10`, driven by `passing_yards` head +4.50% (68.35 → 71.43 yds). DST went the *other* way (attn_nn aggregate -3.42%, `yards_allowed` -4.70%) — same batch-order drift, but DST's loss surface lucked into a better local minimum at the new ordering. Other positions moved in noise. The variance across positions is what makes "per-position fallback" the wrong framing — the bug is one bug, the impact distribution is a function of per-position loss-surface sensitivity to batch ordering, with `passing_yards`'s Huber-δ=15 / ~250 yds/game magnitude making QB the loudest signal.
- **Fix:** `torch.randperm(self._n)` defaults to `device='cpu'` and consumes `torch.default_generator` — the CPU stream that `seed_everything()` seeds and that `DataLoader(shuffle=True)`'s `RandomSampler` also reads from. `.to(self._device)` ships the resulting int64 permutation tensor to the GPU. For N≈20k that's a ~160 KB single H2D copy / ~50 μs per epoch — negligible vs the ~100s of NN forward/backward per epoch, and many orders of magnitude smaller than the DataLoader IPC + per-batch H2D copy that PR #309 removed. Not *bit-identical* to the old DataLoader's `RandomSampler.__iter__` (which constructs a transient `torch.Generator` per epoch and consumes one int64 from the global RNG as the seed for its `torch.randperm` call), but the contract — "draw from CPU global RNG so the same seed maps to the same batch order across CPU/MPS/CUDA hosts" — now holds. `tests/test_reproducibility.py` (3 parametrized tests × 6 positions = 18 cases) re-validates the byte-identical-state_dict contract on CPU (where this code path isn't reached); all 18 passed locally. The CUDA-side validation will be the next post-merge `train-batch.yml` run. The fix does not necessarily fully recover the 00c6d10 baseline — PR [#301](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/301)'s FP16 autocast is a *separate* numerical-drift source for QB that was deliberately deferred (handled per-position with `nn_use_amp=False` if needed in a follow-up). **Update 2026-05-21 (post-#313 train-batch validation run):** QB attn_nn aggregate came back within tolerance of the 00c6d10 FP32 baseline on the RNG fix alone. The deferred AMP follow-up is **retired** — no per-position `nn_use_amp=False` is needed for QB.
- **Lesson:** Docstring contract violations are silent corruption when the underlying mechanism is a global. The PR #309 author's intent was "use the CPU global RNG so the GPU-resident path is interchangeable with the DataLoader fallback" — and the comment said as much — but the code did the opposite. `torch.randperm(n, device='cuda')` works syntactically (no error, no warning), runs to completion, returns a deterministic permutation at a CUDA-seeded state, and silently shifts the SGD trajectory away from every preceding run. **Two structural rules to lift**: (1) When PyTorch exposes "per-device default generators" (CPU + CUDA, separate streams), any tensor-allocating randomness primitive whose API takes a `device` argument has a hidden RNG-stream switch. If the intent is "reproduce on the same numerical seed across devices," the safe pattern is `torch.randperm(n)` on CPU then `.to(device)` — *not* `torch.randperm(n, device=…)`. Same applies to `torch.randn`, `torch.randint`, etc. (2) When a refactor swaps a stable, well-known PyTorch utility (`DataLoader(shuffle=True)`) for a hand-rolled equivalent (`_GPUResidentBatcher`), the docstring's claim of "same as the utility" should be backed by a determinism unit test that exercises both paths under the same global seed and compares the first epoch's batch indices. The reproducibility tests in [tests/test_reproducibility.py](tests/test_reproducibility.py) test SAME-DEVICE reproducibility (good for catching dtype/op drift) but don't compare the GPU-resident path against the DataLoader path. Adding that cross-path determinism test would have caught this on PR #309's CI gate before the regression shipped — captured separately as a follow-up. Cross-link: this is the second-order regression downstream of [the BLAS thread cap entry](#fixed-blas-thread-oversubscription-hung-sklearn-ridge_tune-on-t4-after-pr-301-unmasked-the-parallel-cpu-branch) below (PR #307) — unblocking the GPU branch is what exposed the GPU-resident batcher's behavior under real load + a benchmarkable baseline. The PR #301 FP16 contribution to QB's residual drift was captured separately as a follow-up; **retired** when the post-#313 production-validation run brought QB back within tolerance on the RNG fix alone.

They coincide when main hasn't advanced between upstream completion and downstream queue, and diverge on rapid back-to-back merges. `gh run list --commit` filters by the latter; `${{ github.event.workflow_run.head_sha }}` reads the former. **Never use them interchangeably**, especially as dedup keys. Companion structural lesson: dedup-key mechanisms in CI workflows should mirror the writer's identifier exactly — the existing `job-def-revisions/${HEAD_SHA}.txt` pattern from the layer-A race fix already used `workflow_run.head_sha` on both sides and didn't drift; the dedup_check from PR #299 used `workflow_run.head_sha` on the read side but the run-level `head_sha` (via `--commit`) on the implicit write side, and that mismatch was the bug. Companion lesson on diagnostic interpretation: a workflow's overall `conclusion: success` doesn't imply the gated job actually ran — the dedup_check should only mark "trained" runs as successful, not any-job-passed runs. Marker-based dedup gets this right by construction (write step lives in the gated job); query-based dedup over `gh run list --status=success` needs a tighter predicate. - **What:** All four consumers of the `[docs-only]` opt-in tag did a flat substring match against the *entire* commit message (`!contains(head_commit.message, '[docs-only]')` in batch-image; `git log ... --format=%B | grep -qF '[docs-only]'` in the others). Net effect: a perf change shipped without a verifiable benchmark for several merge cycles.

The four consumers each pipe `git log --format=%B` through that filter before `grep -qF '[docs-only]'`. For tests.yml + pre-pr.sh, which scan a multi-commit range, iterate per-commit (`for sha in $(git log --format=%H "$range"); do ...`) rather than catting the range — `git log --format=%B` puts no separator between commits, so a body line of commit N+1 would otherwise look like a subject of commit N. Fixture-tested locally with 4 mock commits — the e802a47-shape body-only-prose commit now correctly evaluates to `docs_only=false`, while the legitimate-tag cases (PR title or `* [docs-only]` constituent subject) still evaluate to `true`. Verification of the recurrence: this PR itself updates [CLAUDE.md](CLAUDE.md) to *describe* the `[docs-only]` feature; with the old substring check, this PR would have skipped its own image rebuild. The new subject-line filter correctly evaluates this PR's commit subject (a `fix(ci):` subject) as `docs_only=false`.
- **Lesson:** When a sentinel substring serves as a control-plane signal in commit messages, the matcher needs to distinguish "the author tagged this commit" from "the author talked about the tag." `[docs-only]` in `* [docs-only] fix typo` (constituent subject) IS the signal; `[docs-only]` in `the [docs-only] opt-in now also clears X` (prose) IS NOT. Restricting the match to *where authors put control signals* (subject lines, not body prose) handles both squash-merge formats and prevents the meta-bug where any commit that updates the matcher itself triggers its own skip. Companion lesson on dogfooding: a CI control-signal that fires on prose mentions makes the feature uneditable — the next PR that touches `[docs-only]`-handling code, even to fix a bug in it, will dogfood-skip the workflows it just modified, masking whether the fix actually works. Subject-line scoping is the structural fix; "don't mention the feature in commit messages" was the working-around-it fix the matcher's flaw forced on authors. Operationally: when a workflow expression's matcher needs more than `contains()`/`startsWith()`/`endsWith()`, the fix is almost always "move it to a shell-backed leading job whose output gates the real job" — workflow expressions are intentionally underpowered.

PR #367 was based on `39aa8a6`; mid-review, PR [#368](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/368) (`0a17b4e [docs-only] chore(routines): version-control claude-audit prompt as runtime shim`) merged to main. `0a17b4e` fell inside `39aa8a6..<#367 merge head>`, so the scan tripped `docs_only=true` and emitted `shards=[]` — skipping QB/RB/WR/TE/K/DST/shared even though #367 changed `src/serving/app.py` and a test file. `tests-pass` went green via its `test=skipped` branch (a false green); `gh pr checks` showed `test  skipping  0` next to `tests-pass  pass`. The `[docs-only]` subject-line filter (`awk 'NR==1 || /^\* /'`) is preserved verbatim — this fix changes only the *range*, not the *matcher*. New [tests/scripts/test_detect_range.py](tests/scripts/test_detect_range.py) builds a synthetic repo of the #367 shape and asserts `HEAD^2 --not HEAD^1` excludes the unrelated main `[docs-only]` commit (and that the old `base..HEAD` range would NOT have — documenting the bug), plus positive controls (the PR's own `[docs-only]` commit / a `* [docs-only]` squash bullet still trip) and the linear-fallback path. Verified end-to-end against the real `scope_positions` helper: the #367-shape PR now emits `shards=["shared"]`, the old scan emitted `docs_only=true → shards=[]`.

[batch-image.yml](.github/workflows/batch-image.yml)'s `check-docs-only` scans a single commit (`github.event.head_commit.id`), not a range. [.claude/hooks/pre-pr.sh](.claude/hooks/pre-pr.sh) anchors on `git merge-base origin/main HEAD` (a dynamically-computed fork point) on the real local branch HEAD. All four were left functionally as-is except for tests.yml; `_detect-positions.yml` got a comment warning future readers off "fixing" its correct `HEAD^..HEAD`.
- **Lesson:** A control-plane scan that runs on a PR's `refs/pull/N/merge` commit must scope to the PR's own commits via the merge parents (`HEAD^2 --not HEAD^1` / `HEAD^1...HEAD^2`), never via `github.event.pull_request.base.sha` — a *static, lagging* field; once main advances past it, `base.sha..HEAD` is a superset of the PR. The failure mode is the worst kind: a **false green** (skipped tests reported as passing), laundered into a required-check pass by a `skipped`-treated-as-success aggregator. When auditing "does sibling consumer X have this bug too?", the discriminator is not the surface command (`grep [docs-only]`) but **what the range's base resolves to at run time** — a synthetic merge-preview HEAD + a stale base field is the toxic combination; a real post-merge `HEAD^`, a single pushed commit, or a computed `merge-base` are all safe. Cross-link: the subject-line filter from the entry above (`[docs-only]` substring-match) is the *matcher* half of this subsystem; this entry is the *range* half. Both are needed for the opt-in to be correct.

Job-definition revision pinning from PR [#278](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/278) prevents duplicate *Batch job* submissions (queue counts confirmed only one image-SHA × position combo per SHA), so the duplicates wasted CI minutes but didn't double-train. Pre-existing comment at train-batch.yml:26-31 explicitly opted *out* of concurrency to allow Spot fan-out from rapid back-to-back pushes — a cross-PR parallelism property that's worth preserving but doesn't justify same-SHA duplication.
- **Fix:** Two layers. (1) **Concurrency** keyed by `github.event.workflow_run.head_sha || github.sha` — different SHAs get different groups (cross-PR Spot fan-out preserved), but same-SHA fires queue serially. `cancel-in-progress: false` because canceling a run mid-Batch-submit could orphan jobs at the AWS layer (the first run's submitted Batch jobs would keep running with no CI tracking). (2) **Dedup early-exit** via a new `dedup_check` job (parallel with `detect`, so total overhead is `max(detect, dedup_check) ≈ 1 min`, not `detect + dedup_check`): under `workflow_run`, query `gh run list --workflow=train-batch.yml --status=success --head-sha <SHA>` excluding the current run; if any prior success exists, set `skip=true`; `train` job's `if:` reads that output and short-circuits. Under `workflow_dispatch`, `dedup_check` bypasses (manual dispatches are operator-driven and always run). Net effect: same-SHA duplicates now spend ~1 min on detect + dedup-API-call → train-skip, instead of ~15 min on full detect → checkout → install → submit → wait → benchmark-append → ECS-refresh. The concurrency layer also bounds wall-clock: a 3rd or 4th queued duplicate doesn't run in parallel, it waits for the prior to finish — by which time the prior is in either `success` (dedup short-circuits) or `failure` (dedup proceeds, useful as a retry). The two-layer design is necessary because either layer alone has a gap: concurrency alone still spends full CI on the queued run; dedup alone races (two parallel runs would both see "no prior success" and both run).
- **Lesson:** GitHub Actions workflow_run delivery is at-least-once, not exactly-once — any downstream workflow that fans out into expensive work on `workflow_run.completed` should serialize same-SHA fires *and* dedup mid-run, not just one or the other. Companion lesson on debugging the hypothesis: the user's initial "operator manually re-ran batch-image.yml" theory matched the symptom (duplicate downstream fires) but contradicted the data (`run_attempt: 1` everywhere). Confirming root cause via the API field that *would* differentiate the hypothesized cause (manual rerun → `run_attempt > 1`) from the actual cause (GitHub multi-delivery → `run_attempt == 1`) was the critical step — without that field check, the "fix" might have been a more elaborate version of "tell operators to stop manually retrying batch-image" which would have done nothing. Companion lesson on concurrency-group keys: keying by `github.run_id` would serialize ALL train-batch runs into one queue (bad — kills cross-PR Spot fan-out); keying by `github.event.workflow_run.id` would let duplicates from the same upstream still run in parallel (bad — that's exactly what we're trying to prevent); keying by `head_sha` is the right granularity. Cross-PR parallelism + same-SHA dedup, expressed in one group-key expression.

### [FIXED] Huber delta asymmetry across targets starved count heads
- **Files:** Position config files (`*_config.py`)
- **What:** Pre-rebalance loss weights were roughly equal across heads, so yards targets (δ ≈ 15–30) dominated count-head gradients (δ ≈ 0.25–0.5) by ~20–2500× per sample, collapsing the count heads toward their mean. The DST `pts_allowed_bonus` head also had a too-forgiving delta relative to its range, and the old QB `td_points` delta was too small relative to its point scale.
- **Fix:** (1) Rebalanced NN loss weights to ≈ `2.0 / huber_delta` per head across RB (`d229830`), QB (`4ac478f`), WR (`35e611b`), and TE (`a03f795`). (2) DST targets were migrated to 10 raw stats (`cc0c627`), retiring `pts_allowed_bonus` entirely; QB's `td_points` was likewise replaced by split `passing_tds`/`rushing_tds` heads with δ = 0.5 and matching w = 4.0.
- **Lesson:** Huber δ and loss weight are coupled — changing one without the other either starves or drowns a head. Encode the pairing in the config (`2.0/δ`) and re-derive the weight whenever δ moves. See CLAUDE.md "Loss weights are tuned inverse-to-Huber-delta".
