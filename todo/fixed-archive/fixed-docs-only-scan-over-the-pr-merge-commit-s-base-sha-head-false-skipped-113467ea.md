### [FIXED] `[docs-only]` scan over the PR merge commit's `base.sha..HEAD` false-skipped tests.yml's entire fan-out (false green)
- **File(s):** [.github/workflows/tests.yml](../../.github/workflows/tests.yml) (`detect` job's `scope` step — replaced the `github.event.pull_request.base.sha..HEAD` range with parent-relative scoping: `HEAD^2 --not HEAD^1` for the commit-subject scan + `HEAD^1...HEAD^2` for the `scope_positions` diff, with a `HEAD~1..HEAD` fallback for linear/push history; dropped the now-unused `EVENT`/`BASE_SHA` env), [.github/workflows/_detect-positions.yml](../../.github/workflows/_detect-positions.yml) (clarifying comment only — this file was checked and is NOT affected; see Lesson), [tests/scripts/test_detect_range.py](../../tests/scripts/test_detect_range.py) (new git-range regression test reproducing the PR #367 scenario). Confirmed via PR [#367](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/367) on 2026-05-29.
- **What:** On a `pull_request` event GitHub checks out the synthetic merge commit `refs/pull/N/merge` ("Merge <pr-head> into <main-tip>"), so `HEAD` already contains the live main tip. The `detect` job scanned `github.event.pull_request.base.sha..HEAD` for a `[docs-only]` commit subject. `base.sha` is the base recorded when the PR event fired and lags the live main tip, so the range swept in **every commit merged to main after the PR's base**, not just the PR's own commits. PR #367 was based on `39aa8a6`; mid-review, PR [#368](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/368) (`0a17b4e [docs-only] chore(routines): version-control claude-audit prompt as runtime shim`) merged to main. `0a17b4e` fell inside `39aa8a6..<#367 merge head>`, so the scan tripped `docs_only=true` and emitted `shards=[]` — skipping QB/RB/WR/TE/K/DST/shared even though #367 changed `src/serving/app.py` and a test file. `tests-pass` went green via its `test=skipped` branch (a false green); `gh pr checks` showed `test  skipping  0` next to `tests-pass  pass`. Rebasing #367 onto current main (advancing the effective base past `0a17b4e`) masked it, but the workflow bug remained.
- **Fix:** Scope the scan to the PR's OWN commits via the merge commit's parents: `HEAD^1` is the main tip, `HEAD^2` is the PR head, so `git log HEAD^2 --not HEAD^1` is exactly the PR's commits regardless of how far main advanced past `base.sha`. The `scope_positions` diff likewise moves to `git diff HEAD^1...HEAD^2` (three-dot = changes since the fork point); the old `base.sha..HEAD` two-dot diff over-included main's files, which only over-triggered shards (conservative) but was imprecise. Fallback for linear history (push to main after a squash merge, or a conflicted PR whose merge commit can't be computed so checkout lands on the PR head, where `HEAD^2` doesn't exist): `HEAD~1..HEAD`. The `[docs-only]` subject-line filter (`awk 'NR==1 || /^\* /'`) is preserved verbatim — this fix changes only the *range*, not the *matcher*. New [tests/scripts/test_detect_range.py](../../tests/scripts/test_detect_range.py) builds a synthetic repo of the #367 shape and asserts `HEAD^2 --not HEAD^1` excludes the unrelated main `[docs-only]` commit (and that the old `base..HEAD` range would NOT have — documenting the bug), plus positive controls (the PR's own `[docs-only]` commit / a `* [docs-only]` squash bullet still trip) and the linear-fallback path. Verified end-to-end against the real `scope_positions` helper: the #367-shape PR now emits `shards=["shared"]`, the old scan emitted `docs_only=true → shards=[]`.
- **Why the siblings were NOT affected:** [_detect-positions.yml](../../.github/workflows/_detect-positions.yml) (training detect, shared by `train-batch.yml`/`train-ec2.yml`) runs only on `workflow_run`/`workflow_dispatch` (post-merge) and checks out `github.event.workflow_run.head_sha` — a **real main commit** — so its `HEAD^` is the genuine predecessor and `HEAD^..HEAD` correctly scopes to the squash/merge that landed; it has no `base.sha`-style lag and applying `HEAD^2 --not HEAD^1` there would actually regress its non-squash-merge handling. [batch-image.yml](../../.github/workflows/batch-image.yml)'s `check-docs-only` scans a single commit (`github.event.head_commit.id`), not a range. [.claude/hooks/pre-pr.sh](../../.claude/hooks/pre-pr.sh) anchors on `git merge-base origin/main HEAD` (a dynamically-computed fork point) on the real local branch HEAD. Each of those bases is a *real ref that can't lag*; tests.yml was unique in ranging from a static, stale event field over a synthetic merge HEAD. All four were left functionally as-is except for tests.yml; `_detect-positions.yml` got a comment warning future readers off "fixing" its correct `HEAD^..HEAD`.
- **Lesson:** A control-plane scan that runs on a PR's `refs/pull/N/merge` commit must scope to the PR's own commits via the merge parents (`HEAD^2 --not HEAD^1` / `HEAD^1...HEAD^2`), never via `github.event.pull_request.base.sha` — a *static, lagging* field; once main advances past it, `base.sha..HEAD` is a superset of the PR. The failure mode is the worst kind: a **false green** (skipped tests reported as passing), laundered into a required-check pass by a `skipped`-treated-as-success aggregator. When auditing "does sibling consumer X have this bug too?", the discriminator is not the surface command (`grep [docs-only]`) but **what the range's base resolves to at run time** — a synthetic merge-preview HEAD + a stale base field is the toxic combination; a real post-merge `HEAD^`, a single pushed commit, or a computed `merge-base` are all safe. Cross-link: the subject-line filter from the entry above (`[docs-only]` substring-match) is the *matcher* half of this subsystem; this entry is the *range* half. Both are needed for the opt-in to be correct.
