### [FIXED] Concurrent thread-backend tune trials crash CUDA graph capture (cudaErrorIllegalState)
- **File(s):** [../src/tuning/tune_nn.py](../../src/tuning/tune_nn.py) (`_force_eager_for_concurrent_thread_trials` + `main()` ordering); tests in [../tests/tuning/test_tune_nn.py](../../tests/tuning/test_tune_nn.py); context in [gpu_launch_bound_levers.md](../gpu_launch_bound_levers.md) § "Thread-vs-MPS backend A/B (2026-06-11)".
- **What:** Measured on AWS Batch 2026-06-11 (g6.xlarge/L4, job `614ae7d7`, the thread-vs-MPS A/B's thread arm): `tune_nn --parallel-backend thread --n-jobs 4` with CUDA graphs enabled crashes with `torch.AcceleratorError: CUDA error: the operation cannot be performed in the present state` (`cudaErrorIllegalState`) inside `MultiHeadTrainer._maybe_graph_model` → `torch.cuda.make_graphed_callables` → `capture_begin`. `torch.cuda.graph` captures in the default **global** mode, which errors when any OTHER thread in the process has in-flight GPU work — with `n_jobs>1` Optuna threads sharing one process, one trial's capture races every other trial's kernel launches. Also a latent crash lottery for local tuning: since the 2026-06-05 autodetect-ON cutover, an sm_80+ box (5080) on the default `thread --n-jobs 2` captures in both trial threads. The MPS process backend is immune (per-process capture state).
- **Fix:** `_force_eager_for_concurrent_thread_trials(parallel_backend, n_jobs)`: when the resolved backend is `thread` AND resolved `n_jobs>1` AND `cuda_graph_enabled()` (the actual capture decision, not a raw env read), set `FF_CUDA_GRAPH=0` + `FF_CUDA_GRAPH_FULL=0` (the full-step capture shipped in #1122 shares the constraint and gates on the base resolver anyway) **before** `_resolve_storage_version` so the study lands in the eager `scheduler_v2` namespace the trials actually train under, and print a one-liner citing `cudaErrorIllegalState`. `n_jobs==1` thread mode and the mps backend stay graphed. A capture lock was rejected: it only serializes captures, but global-mode capture also conflicts with other threads' *ordinary* kernel launches mid-capture, so eager is the only safe thread-concurrent configuration.
- **Lesson:** CUDA graph capture is process-global state, not per-thread: any in-process trial concurrency must force the eager path — locks can't make global-mode capture coexist with other threads' kernel launches. And when a guard mutates an env knob that namespacing/provenance also key on, order the mutation before the resolution so the recorded regime matches what ran.
