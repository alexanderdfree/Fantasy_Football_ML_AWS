### [FIXED] `_GPUResidentBatcher` drew permutations from CUDA RNG, diverging the per-epoch batch order from the CPU/MPS DataLoader path
- **Files:** [src/shared/training.py](../../src/shared/training.py) (one-line fix in `_GPUResidentBatcher.__iter__`: `torch.randperm(self._n, device=self._device)` → `torch.randperm(self._n).to(self._device)`; expanded the surrounding docstring to spell out the CPU/CUDA RNG stream split). No subclass overrides — every position inherits the fix because `_GPUResidentBatcher` is the single class all four `make_*_dataloaders` instantiate on CUDA.
- **What:** PR [#309](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/309) (`04ef622`) introduced `_GPUResidentBatcher` to replace the CUDA-side `DataLoader` path. Its `__iter__` generated the per-epoch permutation via `torch.randperm(self._n, device=self._device)` (i.e. on the CUDA device). The docstring claimed this matched "DataLoader's default RandomSampler when constructed with `generator=None`" — false. PyTorch maintains *independent* default generators per device: `torch.default_generator` (CPU) and `torch.cuda.default_generators[i]` (CUDA). `seed_everything(42)` in [src/shared/utils.py](../../src/shared/utils.py) seeds both via `torch.manual_seed(42)` + `torch.cuda.manual_seed_all(42)`, but they're separate streams that produce different sequences at the same numeric seed. The old `DataLoader(shuffle=True)` consumed the CPU stream (via `RandomSampler`); the new `_GPUResidentBatcher` switched to the CUDA stream silently. Same seed, different batch order per epoch on CUDA hosts → a real divergence in the SGD trajectory vs the CPU/MPS path (and vs every pre-PR-#309 production run, which had used DataLoader on CUDA). The bug was universal across all 6 positions — every one of them generates fresh permutations through this single code path. The bug only became *visible* as a QB MAE regression in the PR #307 production-validation run (2026-05-21 ~11:24 UTC, 6 successful jobs against image `04ef622`): QB attn_nn aggregate +2.68% vs FP32 baseline `00c6d10`, driven by `passing_yards` head +4.50% (68.35 → 71.43 yds). DST went the *other* way (attn_nn aggregate -3.42%, `yards_allowed` -4.70%) — same batch-order drift, but DST's loss surface lucked into a better local minimum at the new ordering. Other positions moved in noise. The variance across positions is what makes "per-position fallback" the wrong framing — the bug is one bug, the impact distribution is a function of per-position loss-surface sensitivity to batch ordering, with `passing_yards`'s Huber-δ=15 / ~250 yds/game magnitude making QB the loudest signal.
- **Fix:** `torch.randperm(self._n)` defaults to `device='cpu'` and consumes `torch.default_generator` — the CPU stream that `seed_everything()` seeds and that `DataLoader(shuffle=True)`'s `RandomSampler` also reads from. `.to(self._device)` ships the resulting int64 permutation tensor to the GPU. For N≈20k that's a ~160 KB single H2D copy / ~50 μs per epoch — negligible vs the ~100s of NN forward/backward per epoch, and many orders of magnitude smaller than the DataLoader IPC + per-batch H2D copy that PR #309 removed. Not *bit-identical* to the old DataLoader's `RandomSampler.__iter__` (which constructs a transient `torch.Generator` per epoch and consumes one int64 from the global RNG as the seed for its `torch.randperm` call), but the contract — "draw from CPU global RNG so the same seed maps to the same batch order across CPU/MPS/CUDA hosts" — now holds. `tests/test_reproducibility.py` (3 parametrized tests × 6 positions = 18 cases) re-validates the byte-identical-state_dict contract on CPU (where this code path isn't reached); all 18 passed locally. The CUDA-side validation will be the next post-merge `train-batch.yml` run. The fix does not necessarily fully recover the 00c6d10 baseline — PR [#301](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/301)'s FP16 autocast is a *separate* numerical-drift source for QB that was deliberately deferred (handled per-position with `nn_use_amp=False` if needed in a follow-up). **Update 2026-05-21 (post-#313 train-batch validation run):** QB attn_nn aggregate came back within tolerance of the 00c6d10 FP32 baseline on the RNG fix alone. The deferred AMP follow-up is **retired** — no per-position `nn_use_amp=False` is needed for QB.
- **Lesson:** Docstring contract violations are silent corruption when the underlying mechanism is a global. The PR #309 author's intent was "use the CPU global RNG so the GPU-resident path is interchangeable with the DataLoader fallback" — and the comment said as much — but the code did the opposite. `torch.randperm(n, device='cuda')` works syntactically (no error, no warning), runs to completion, returns a deterministic permutation at a CUDA-seeded state, and silently shifts the SGD trajectory away from every preceding run. **Two structural rules to lift**: (1) When PyTorch exposes "per-device default generators" (CPU + CUDA, separate streams), any tensor-allocating randomness primitive whose API takes a `device` argument has a hidden RNG-stream switch. If the intent is "reproduce on the same numerical seed across devices," the safe pattern is `torch.randperm(n)` on CPU then `.to(device)` — *not* `torch.randperm(n, device=…)`. Same applies to `torch.randn`, `torch.randint`, etc. (2) When a refactor swaps a stable, well-known PyTorch utility (`DataLoader(shuffle=True)`) for a hand-rolled equivalent (`_GPUResidentBatcher`), the docstring's claim of "same as the utility" should be backed by a determinism unit test that exercises both paths under the same global seed and compares the first epoch's batch indices. The reproducibility tests in [tests/test_reproducibility.py](../../tests/test_reproducibility.py) test SAME-DEVICE reproducibility (good for catching dtype/op drift) but don't compare the GPU-resident path against the DataLoader path. Adding that cross-path determinism test would have caught this on PR #309's CI gate before the regression shipped — captured separately as a follow-up. Cross-link: this is the second-order regression downstream of [the BLAS thread cap entry](../fixed-archive.md#fixed-blas-thread-oversubscription-hung-sklearn-ridge_tune-on-t4-after-pr-301-unmasked-the-parallel-cpu-branch) below (PR #307) — unblocking the GPU branch is what exposed the GPU-resident batcher's behavior under real load + a benchmarkable baseline. The PR #301 FP16 contribution to QB's residual drift was captured separately as a follow-up; **retired** when the post-#313 production-validation run brought QB back within tolerance on the RNG fix alone.
