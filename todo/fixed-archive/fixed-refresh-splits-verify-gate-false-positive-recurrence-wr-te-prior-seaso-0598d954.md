### [FIXED] refresh-splits verify gate false-positive recurrence: WR/TE `prior_season_mean_catch_rate` → S3 splits silently stale for 2 days
- **File(s):** [../.github/workflows/refresh-splits.yml](../../.github/workflows/refresh-splits.yml) (`runtime_added_per_pos` carve-out map + new `File issue on failure` step + `issues: write`), [../tests/test_refresh_splits_workflow.py](../../tests/test_refresh_splits_workflow.py) (ast-parsed carve-out assertions + self-deriving coverage test + alert-step contract).
- **What:** PRs #1061 (WR) and #1082 (TE) added `prior_season_mean_catch_rate` to `include_features["prior_season"]` — a col computed at *training* time by `src/{wr,te}/features.py`, never present in `data/splits/*.parquet` — without extending the verify step's `runtime_added_per_pos` carve-out map (which only listed RB, from the identical PR #337 incident). Every refresh-splits run from 2026-06-08T08:32 failed the column-presence gate *before* the S3 upload (`WR: 1 missing — ['prior_season_mean_catch_rate']`, `TE: …`), so S3 `data/splits/` silently lagged main for ~2 days (7 failed runs) while merges that change split content (stint-aware rolling #722/#666, dedup pre-sorts, red-zone priors) trained on stale data. Nobody noticed until a Codex audit read the failed run. The parquets were correct; the gate was wrong — same class as #337, and the config comments documenting "derived in features.py" did not prevent the recurrence.
- **Fix:** Added WR/TE carve-out entries; extended the gate's SystemExit message to name the carve-out map as a likely cause; added a self-deriving unit test that regex-scans each position's `features.py` for literal `df["col"] =` assignments, intersects with `flatten_include_features − specific_features`, and requires each hit to be carved out — so the next offending PR fails its own unit shard at PR time (rule verified exact today: RB×2, WR×1, TE×1, QB ∅, zero false positives). Added an `if: failure()` step that files/refreshes a `[refresh-splits] run failed` GitHub issue so a broken refresh lands in the issue backlog instead of going unnoticed.
- **Lesson:** A hardcoded exception map duplicating knowledge that lives in code (which cols `features.py` computes) WILL drift — derive the requirement in a contract test instead of documenting it in comments (#337's comment didn't stop #1061). And a workflow whose *effect* is keeping shared state fresh (S3 splits) needs affirmative failure alerting: its failure mode is silent staleness, which no downstream consumer surfaces.
