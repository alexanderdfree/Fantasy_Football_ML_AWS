### [FIXED] `ecs_refresh_sentinel` belt-and-suspenders removed after in-flight refresh proven live across 3 retrain cycles
- **File(s):** [.github/workflows/train-batch.yml](../../.github/workflows/train-batch.yml) (deleted `Kick off ECS rolling deploy (non-blocking)` step + `ecs_refresh_sentinel` job — 68 lines removed), [docs/ARCHITECTURE.md](../../docs/ARCHITECTURE.md) (D14 body past-tensed at line 503 + new 2026-05-21 Update history entry).
- **What:** PR [#302](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/302) shipped the in-flight per-position model refresh (gunicorn `on_starting` daemon polls `models/{POS}/manifest.json` etags every 30 s and atomic-swap-rename the on-disk `models/` dir). train-batch.yml kept the prior delivery path — an `aws ecs update-service --force-new-deployment` kick after benchmark commit, plus an `ecs_refresh_sentinel` `services-stable` wait job — as belt-and-suspenders. The D14 ADR's planned retirement criterion was "remove after the in-flight path runs cleanly for ~2 retrain cycles."
- **Fix:** Verified on 2026-05-21 across 3 retrain cycles (runs #80/#81/#82, all SHA `9409e7e` triggered by the rapid 3-burst of `chore(ci): append Batch benchmark run` commits). CloudWatch `aws logs filter-log-events --log-group-name /ecs/fantasy-predictor --filter-pattern 'swapped to new manifest'` returned 36 events across the two long-running serving tasks (`3c32e6fb` + `9bfef166`). Timeline: first in-flight swap (K, 16:08:41Z) preceded the ECS update-service kick (16:11:24Z) by ~2 min 43 s; the entire six-position fan-out was live on both running tasks by 16:11:24Z; ECS rolling deploy spun up a new task (`ccfcb589`, 16:13:43Z) that bootstrap-loaded the post-train manifest etags directly (zero swap events needed); `ecs_refresh_sentinel`'s `services-stable` returned at 16:19:59Z — ~9 min after the in-flight had finished delivery. Filter for `?"did_refresh=False" ?"refresh failed" ?"falling back to current" ?"falling back to previous"` returned zero matches in the extended window — no fail-soft fallbacks observed across the 36 swaps. Bonus: the in-flight refresh actively recovered task `3c32e6fb` from a degraded RB state (NaN'd ridge/nn/lgbm/attn_nn predictions due to feature-count drift inherited from the prior deploy's stale RB scaler) when the new RB manifest landed at 16:09:42Z — concrete evidence that the in-flight path handles the exact failure mode the sentinel was guarding. Removal deletes only the workflow-level belt-and-suspenders; the per-container `src/{pos}/outputs/.refreshed_at` sentinel file (read by `_ensure_position_loaded` to detect on-disk swaps) and the in-flight poller (`src/shared/model_sync.py::start_refresh_poller`) are unaffected — they remain load-bearing. [.github/workflows/train-ec2.yml](../../.github/workflows/train-ec2.yml) keeps its ECS kick: it's the `BATCH_ACTIVE=false` rollback path and the conservative posture there is intentional.
- **Lesson:** The "kept as belt-and-suspenders for ~2 retrain cycles" pattern is the right shape for shipping risky-but-better delivery mechanisms: ship the new path live behind the old one, prove the new path in production logs, then remove the fallback. The criterion for retirement is **evidence in the right place** — workflow status alone cannot distinguish "in-flight worked" from "ECS rolling deploy worked"; only serving-side CloudWatch logs can. **Structural rule:** when designing a retirement criterion for a fallback, require the verification signal to be the actual mechanism firing (here: `[refresh] {POS} swapped to new manifest etag=... source=stable` log lines on the serving container), not a downstream proxy (workflow `services-stable` succeeding doesn't prove the in-flight path actually did anything). Companion lesson on naming-collision: `ecs_refresh_sentinel` (the workflow job) and `.refreshed_at` (the per-container file) share the word "sentinel" but solve different problems — the file is the request-path detection mechanism for the in-flight swap; the job was the workflow-level confirmation that ECS rolling deploy converged. Sole-mechanism removal targets the *workflow* artifact; touching the file would have broken the in-flight path the sentinel job was protecting.
