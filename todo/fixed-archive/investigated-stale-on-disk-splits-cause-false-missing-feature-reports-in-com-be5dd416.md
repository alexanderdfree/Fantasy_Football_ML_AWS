### [INVESTIGATED] Stale on-disk splits cause false "missing feature" reports in completeness analysis
- **File(s):** `data/splits/{train,val,test}.parquet` (data artifact, not source); `src/analysis/analysis_data_completeness.py` (the audit). Investigation via `analysis_output/confirm_completeness.py` → `analysis_output/rebuild_and_check.py` (both gitignored transient scripts, not in the repo).
- **What:** Running `analysis_data_completeness.py` (or any script that compares the on-disk splits' columns to `get_feature_columns()`) against a stale `data/splits/` showed **7–9 "missing" feature columns per skill position** — all external-source features: `contract_*`, `prior_season_*_exp` (ff-opportunity), `prior_season_mean_qbr_total`, `prior_season_mean_pts_added`, `prior_season_*_redzone_*`. This looks like a production gap but is a false positive: `engineer.build_features` merges these at split-build time; the local splits (mtime Apr 27) were simply ~5 weeks old and predated their addition to the whitelist. Rebuilt splits (from `data/raw`) had **312 cols vs the stale 277**, all 7–9 columns present, all positions ✅.
- **Why it matters:** The `feature_build.py:81` KeyError guard fires in production if any whitelisted column is absent, so a production pipeline *can't* train on missing columns silently. But a standalone analysis script reading the on-disk split against `get_feature_columns()` offline will cry wolf if the splits lag. This can falsely prompt a "fix" to `src/features/engineer.py` for a column that's already correctly produced.
- **Resolution:** Rebuild splits before any column-presence audit. `analysis_data_completeness.py` documents this caveat explicitly and adds a `--rebuild` flag. The existing memory entry `feedback_worktree_splits_stale` covers the pipeline-error form; this extends it to the analysis-false-positive form.
- **Lesson:** Diffing the on-disk split's column set against the current `get_feature_columns()` whitelist is **only valid when splits are fresh**. The canonical completeness check is always `--rebuild` (the production recipe: `build_features(preprocess(load_raw_data())) → temporal_split`) followed by the feature build for each position. A stale split gives a false "missing" reading that resolves on rebuild — don't file a bug or propose an `engineer.py` fix before rebuilding first.
