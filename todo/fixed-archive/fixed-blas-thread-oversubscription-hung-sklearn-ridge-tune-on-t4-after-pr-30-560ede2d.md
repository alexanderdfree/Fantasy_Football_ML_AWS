### [FIXED] BLAS thread oversubscription hung sklearn ridge_tune on T4 after PR #301 unmasked the parallel CPU branch
- **Files:** [.github/workflows/batch-image.yml](../../.github/workflows/batch-image.yml) (jq filter that already manages the `NN_DATALOADER_NUM_WORKERS=3` job-definition env var extended to also pin `OMP_NUM_THREADS=1`, `MKL_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1`, `NUMEXPR_NUM_THREADS=1`). No `pipeline.py` / `models.py` code change — the workflow-level cap is sufficient and per-submission `containerOverrides` in `src/batch/launch.py` still take precedence if a future workload needs to bump BLAS threads for a specific position.
- **What:** The FP16 production validation run after PR [#301](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/301) (workflow_dispatch 26218950001, 2026-05-21 09:56 UTC) saw 5 of 6 Batch jobs wedge at the 30-min timeout. CloudWatch logs showed two distinct symptoms depending on which host: (a) pre-NN-train hang — `=== {pos} Multi-Head Neural Net ===` printed and then silence, no epoch logs; (b) post-attn_nn_train hang — `[timing] phase=attn_nn_train seconds=X` printed cleanly, then silence. Both share one root: `_tune_ridge_alphas_cv` in the parallel CPU branch via `joblib.Parallel(n_jobs=-1, prefer="threads")` while the GPU branch is also live. Each joblib thread invokes a Ridge solve that delegates to BLAS, which defaults `OMP_NUM_THREADS = nproc = 4` on the host. Resulting thread budget on a 4-vCPU g4dn.xlarge T4: 4 joblib threads × 4 BLAS threads each + 3 DataLoader worker subprocesses + 1 main GPU thread ≈ 19 thread slots on 4 cores = ~5× oversubscription. Under that load OpenBLAS intermittently deadlocks in its thread-pool lock. PR [#293](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/293) (BF16 autocast) had been masking the issue for the prior week — BF16 hung the GPU branch immediately on T4 (sm_75 has no native BF16 Tensor Cores — see PR [#301](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/301)'s commit message + [src/shared/training.py](../../src/shared/training.py) docstring for the dtype × compute-capability matrix), so the CPU branch had the cores to itself and ridge_tune happened to fit. PR #301 fixed the BF16 hang → CPU and GPU branches now actually overlap as the PR [#267](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/267) ThreadPoolExecutor design intended → BLAS oversubscription surfaced. Live diagnostic that pinned the phase: DST + WR-newer printed `attn_nn_train seconds=X` and then `cpu_future.result()` blocked indefinitely on the still-hung Ridge; `[timing] phase=ridge_tune` was *never* logged. The hang isn't *post-train* — it's been hung in ridge_tune the entire time, hidden behind the parallel GPU branch's normal logs.
- **Fix:** Pinned single-threaded BLAS at the job-definition level via the same jq filter that already managed `NN_DATALOADER_NUM_WORKERS=3`. With OMP/MKL/OPENBLAS/NUMEXPR all at 1, the joblib n_jobs=-1 = 4 threads each do their own BLAS solve in 1 thread = exact 4-core fan-out, no overcommit. **Verified** by a single DST job (`ff-dst-verify-omp1-1779359690-A34E55`) submitted manually against revision-60 of the job def with the thread caps as containerOverrides: `ridge_tune=6.1s`, `attn_nn_train=87.8s` (beat PR #293's 110s target), `total=225s`, exit code 0. Same DST job without the caps had hung indefinitely 25 min earlier in the same Batch run. The fix promotes those overrides from per-submission to the registered job def so every Batch run inherits them. No `src/shared/pipeline.py` change — the parallel-CPU-branch design from PR #267 is correct, the issue is just the BLAS thread defaults assumed nothing else was using the cores.
- **Lesson:** BLAS thread defaults (`OMP_NUM_THREADS=nproc`) make sense when BLAS is the only multi-threaded workload, but in a hybrid CPU+GPU pipeline with joblib-parallel CPU work and CUDA DataLoader worker subprocesses, the multiplicative math becomes joblib × BLAS + DataLoader workers + main thread — and on a small 4-vCPU host that's already ~5× oversubscribed. The fix is to cap BLAS to 1 thread per process and let the *outer* parallelism axis (joblib here) own the fan-out. The structural lesson: any container that runs sklearn/scipy/numpy concurrent with a Python-thread-managed compute stage should set `OMP_NUM_THREADS=1` (and friends) at the container level, not rely on BLAS's per-call defaults. Companion lesson on debugging masked regressions: PR #293 (BF16-on-T4 hang) was masking PR #267's CPU/GPU overlap design from actually exercising the BLAS pool. Once PR #301 unblocked BF16, this latent hang emerged immediately. **When unblocking a regression, audit downstream consumers of the path that was previously blocked — they may have latent bugs the upstream block was hiding.** Companion lesson on diagnostic reading: `attn_nn_train seconds=X` printed cleanly but the workflow hung — the hang wasn't *in* attention training, it was at the next blocking call in the parent (`cpu_future.result()`). Reading the pipeline source for what executes immediately after the last successful timing log is more reliable than guessing from where the silence "looks" placed.
