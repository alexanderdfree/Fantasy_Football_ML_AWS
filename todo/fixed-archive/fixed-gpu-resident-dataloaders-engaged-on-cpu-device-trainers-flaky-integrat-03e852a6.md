### [FIXED] GPU-resident dataloaders engaged on CPU-device trainers → flaky @integration regression tests on a GPU box
- **File(s):** [../src/shared/training.py](../../src/shared/training.py) (`_gpu_resident_device` + the four `make_*_dataloaders` factories) and [../src/shared/pipeline.py](../../src/shared/pipeline.py) (5 factory call sites). The follow-up to the CUDA-graph device-gate fix above.
- **What:** `make_dataloaders` / `make_history_dataloaders` / `make_history_with_opp_dataloaders` / `make_nested_kick_dataloaders` chose the GPU-resident batcher (`_GPUResidentBatcher`) via `_gpu_resident_device()`, which keyed off the **global** `cuda_enabled()` — not the device the trainer would actually run on. On a GPU box the per-position `@pytest.mark.integration` regression/threshold tests build `MultiHeadTrainer(..., device=torch.device("cpu"))` but called the factories with no device, so they received GPU-resident loaders whose shuffle both differs from the CPU `DataLoader` path and isn't seeded the same way → the tiny synthetic-data NN converged to wildly different minima (qb/rb/wr/dst NN MAE 60–100 vs LGBM 5–15), varying run-to-run. Green on CPU/CI; flaky only on a CUDA-visible dev box. Graph-independent (reproduced with `FF_CUDA_GRAPH=0`); `FF_DEVICE=cpu` masked it (it forces `_gpu_resident_device()`→None).
- **Fix:** Made GPU residency **opt-in by the caller's training device**. `_gpu_resident_device(device)` now returns the resident device only when the passed `device` is CUDA; the four factories take an optional `device=None` (default → plain `DataLoader`); `src/shared/pipeline.py` passes the resolved `_nn_device()` at all five call sites. **Numerically inert on production:** on a GPU host `_nn_device()` is `cuda`, so residency engages with the *same* device as before (byte-identical; e2e pipeline tests pass on GPU). Tests / CPU callers default to `device=None` → the deterministic CPU loader → CI-faithful local runs. Verified on the 5080: all-position regression+training 131 passed ×2 under `-n 8` (was 6 failed), `pytest -m unit` 2536 passed.
- **Lesson:** Same root lesson as the entry above, second instance: a factory that engages a CUDA fast path must learn the *consumer's* device, not sniff global CUDA availability. When the factory runs before the trainer exists (so it can't read `self.device`), thread the intended device in and default residency OFF — production opts in explicitly, tests/CPU stay deterministic. Flipping the default to opt-in fixed every call site with **zero per-test edits** (only the 5 production call sites + the factory signatures changed), not the ~50 test-site churn a default-autodetect-plus-opt-out approach would have needed.
