### [FIXED] Benchmark `git_hash` recorded the wrong SHA on rapid back-to-back merges
- **Files:** `src/batch/benchmark.py` (new `--git-hash` arg, threaded into the `append_to_history` payload), `.github/workflows/train-batch.yml` and `.github/workflows/train-ec2.yml` (pass `--git-hash "$GITHUB_SHA"`). Misleading benchmark rows: `benchmark_history/2026-05-20T10-04-11_adfbce2.json` (note: `Batch Spot auto-run (a7b3145)`) — note correctly carries the image SHA but `git_hash` mislabels it as the workspace HEAD.
- **What:** PR #248's review uncovered an apparent K Ridge "drift" of +0.106 (`3.886` at `adfbce2` → `3.992` at `15d1668`) that looked like a regression caused by the PR #242 / #243 PositionConfig refactor. Reproducing locally at both SHAs showed Ridge = `3.992170810699463` for both — i.e. the refactor was bit-equivalent and the `3.886` row was the outlier. Tracing the workflow: `batch-image.yml` builds the docker image from `workflow_run.head_sha` (in this case `a7b3145`, PR #242's merge), and `train-batch.yml`'s Batch jobs run that image. But the workflow runner's *workspace* then does `git pull --rebase origin main`, which advanced HEAD to `adfbce2` (PR #241, merged ~15 min later). `src/batch/benchmark.py::get_git_hash()` reads workspace HEAD via `git rev-parse --short HEAD`, so the appended JSON recorded `git_hash: adfbce2` — pointing at a SHA the Batch image never trained on. The actual K MAEs in that row reflect `a7b3145`'s code state (pre-PR-241, with PR #239 alone, Ridge `3.886`), exactly as the `[FIXED] K weather features` archive entry documents. The subsequent `15d1668` run trained on a docker image that *did* include PR #241, so its `3.992` matches the post-PR-241 baseline the `[FIXED] K XP-only games` archive predicts.
- **Fix:** Added `--git-hash` to `src/batch/benchmark.py` (CLI arg, threaded into both the `run_id` filename and the JSON's `git_hash` field; falls back to `get_git_hash()` when not set, so local invocations keep working). Both production workflows now pass `--git-hash "$GITHUB_SHA"` — for `workflow_run` events that's `workflow_run.head_sha`, i.e. the SHA the docker image was built from. **[Correction — see the audit-320 entry above: `$GITHUB_SHA` is the *run-level* head_sha, NOT `workflow_run.head_sha`; they diverge on rapid merges. This entry's `$GITHUB_SHA` choice was a partial fix, superseded by `--git-hash "$HEAD_SHA"`.]** The `--note` already carried the correct image SHA via `(${GITHUB_SHA::7})`, so the fix just makes the structured `git_hash` field match what the note already said. No re-anchoring needed: the K Ridge `3.992` / NN `4.025` / Attn `4.075` / LGBM `4.058` post-PR-#241 baseline (recorded inline in the [FIXED] K XP-only games entry below) is the actual production state and matches every `git_hash`-correct CI run + local reproductions.
- **Lesson:** A CI workflow that builds a docker image from one SHA, then trains using that image, then records "the commit this was trained on" by reading the workspace HEAD will mislabel runs whenever main advances during the training window. The mislabel is silent — the JSON looks plausible, the only signal is downstream consumers (MAE comparison tables, "did the refactor regress us?" questions) seeing two consecutive rows that disagree by an amount the actual code couldn't explain. Companion lesson: when a benchmark "drift" exceeds ~0.05 MAE *and* every other position is bit-identical *and* the local pipeline reproduces the post-state at both SHAs, the regression is in the CI provenance, not the code. Diff the recorded `git_hash` against the `note`'s parenthetical SHA before chasing a refactor revert — they should agree.
