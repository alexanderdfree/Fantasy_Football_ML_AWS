### [INVESTIGATED, BENIGN] `snap_pct` imputation groups by raw `(position, week)` (not season-aware) — but the median branch is dead code
- **File(s):** Investigation only, no model change. [src/data/preprocessing.py](../../src/data/preprocessing.py) (`impute_snap_pct`, the `groupby(["position","week"])` median), [src/features/engineer.py](../../src/features/engineer.py) (L290 snap_pct lag), [src/data/split.py](../../src/data/split.py) (the three callers). Surfaced by PR #608; caveat closed in [src/analysis/late_week_effect_findings.md](../../src/analysis/late_week_effect_findings.md).
- **What:** `impute_snap_pct` fills a missing `snap_pct` with the `(position, week)` median, not `(position, season, week)`. Since the NFL went 17→18 regular-season weeks in 2021, "week 17" conflates the ≤2020 *final* (rested-starter, low-snap) week with the 2021+ *penultimate* (normal) week — an era-contaminated median in principle. Same era-awareness principle as the late-week analysis: the rest week is `max(week)` per season (wk17 ≤2020, wk18 ≥2021).
- **Result (why it's benign — empirical):** The median branch **never executes against a real row**. The production chain is `build_features(preprocess(load_raw_data()))` → `temporal_split` (refresh-splits.yml), and `engineer.py:290` zero-fills every `snap_pct` NaN with `groupby(["player_id","season"]).shift(1).fillna(0)` *before* the split. By the time `impute_snap_pct` runs — in `temporal_split` (on that in-memory post-`build_features` frame) and in the CV / rolling-origin folds (which re-read the post-`build_features` on-disk splits) — there are **0 NaN** to fill (confirmed on the on-disk splits: train/val/test all 0.00% NaN `snap_pct`; the 11–21% exact-zero mass is the lag signature, not NaN). The K/DST tuning frames (`tune_lgbm.py`) carry **no `snap_pct` column**, so those callers early-return at the `if "snap_pct" not in df.columns` guard. The era-Δ in the medians it *would* compute is small anyway (week-17 ≤2020 vs ≥2021: QB 0.00, RB −0.02, TE −0.06, WR −0.03, K 0.00 — ≤6 snap-share points).
- **Decision:** No change. `impute_snap_pct`'s median lookup is dead code in every production / CV / benchmark / tuning path. Making the grouping season-aware touches `src/data/`, which force-triggers a guaranteed Δ=0 six-position retrain — indistinguishable from a broken/wrong-path edit and a `benchmark_history` pollutant — to harden a branch that cannot fire. If a future change ever imputes *before* the `engineer.py` lag (or feeds raw multi-era frames into a split fn), switch to `(position, season, week)` then, and add a regression test pinning the post-lag 0-NaN invariant.
- **Lesson:** "Merged on the right key" and "the median math is era-wrong" can both be true while the impact is exactly zero — trace whether the buggy branch is *reachable* on production data before fixing it (here the median lookup runs, but only on a column an upstream step already fully imputed to non-NaN). A `src/data/` "fix" to dead code buys a Δ=0 retrain, not a metric; the verify-the-data-effect discipline cuts both ways. Empirical no-op proof: NaN-count the column the function actually receives, don't reason from the function in isolation.
