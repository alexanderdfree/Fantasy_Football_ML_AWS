### [FIXED] Kickers duplicated in serving — every kicker shown twice (real row + phantom actual≈0 / null-pred twin)
- **File(s):** [src/serving/app.py](../../src/serving/app.py) (`_load_base_data_locked`: new module-level `_APPENDED_POSITIONS` constant + position filter on the base `results` copy), [src/shared/aggregate_targets.py](../../src/shared/aggregate_targets.py) (`TARGET_UNITS` gained the 4 K target keys), [tests/test_app_boot.py](../../tests/test_app_boot.py) (synthetic skill frame now carries kicker rows; new `test_no_phantom_duplicate_kicker_rows`; `test_concat_shape_matches_sum_of_test_splits` subtracts the dropped skill-K/DST rows), [tests/test_app_breakdown.py](../../tests/test_app_breakdown.py) + [tests/test_app_benchmark_history.py](../../tests/test_app_benchmark_history.py) (assert K targets now carry units).
- **What:** `/api/predictions?position=K` returned **1078 rows = 543 phantom + 535 real**; every other position had 0 duplicates. Each kicker player-week appeared twice — a real row (actual + preds) and a phantom twin (`actual`≈0, all preds `null`), so the frontend showed every kicker twice and ~half the K leaderboard was blank. Root cause: `_load_base_data_locked` built the base frame with `results = test[keep_cols].copy()`, copying **all** of the skill-position `test.parquet` — which contains 543 kicker rows (kickers appear in the offensive player-week table with ~0 offensive `fantasy_points`: mean 0.001 / median 0 / max 0.6 from a rare kicker rush-or-reception yard). K is **then** appended separately from its authoritative split (`_load_k_splits`), and predictions write only to the appended rows' index (`results.loc[pos_index]`), so the copied skill-frame kickers stayed `actual`≈0 / null-pred → the phantom twins. **K-only** because team defenses (DST) aren't players in `test.parquet`, so DST is appended once and never doubled. Secondary: the per-stat breakdown drill-down **and** the History tab's `formatTargetMae` rendered kicker stats with no unit suffix because `TARGET_UNITS` was missing all four K target keys.
- **Fix:** Exclude the separately-appended positions from the base copy — `results = test[~test["position"].isin(_APPENDED_POSITIONS)][keep_cols].copy()` with `_APPENDED_POSITIONS = ("K", "DST")` (DST half defensive — not in `test.parquet` today). The `splits` dict still stores the **original** `test` frame, so QB/RB/WR/TE in-place prediction writes are untouched; nothing consumed the phantom rows (they already carried null preds → excluded from MAE). Added the 4 kicker units to `TARGET_UNITS` (`fg_yard_points`/`pat_points` → "pts", `fg_misses`/`xp_misses` → "misses"); both consumers (breakdown drill-down + History tab) pick them up automatically, and K isn't in `POINT_EQUIVALENT_MULTIPLIER` so there's no double-suffix.
- **Lesson:** CI never caught this because the `test_app_boot.py` synthetic skill frame only built QB/RB/WR/TE — the production reality (kickers present in the skill parquet) wasn't mirrored, so the duplication couldn't reproduce. **Mirror the production position mix into serving fixtures**, or a "copy then separately append" assembly silently doubles any position that exists in both sources. The bug was invisible in overall MAE (phantom rows have null preds, excluded) and showed only as junk rows in the position view — a row-count/dedup assertion catches it, an MAE check never would. Distinct from (and does **not** resolve) the still-open `[UNCERTAIN] K/DST index collision in _get_data()` entry above — that's a separate index-offset concern.
