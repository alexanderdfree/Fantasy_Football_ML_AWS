### [FIXED] CUDA-graph capture fired on CPU-device trainers (FF_CUDA_GRAPH) → NaN / flaky NN tests on a GPU dev box
- **File(s):** [../src/shared/training.py](../../src/shared/training.py) (`MultiHeadTrainer._maybe_graph_model` guard, ~L776). Symptom surfaced in `tests/k/test_training.py::TestMultiHeadTrainer::test_losses_decrease` and `tests/k/test_regression.py::test_nn_within_25pct_of_lightgbm` (and the same `device=cpu` trainer pattern in every position's `test_training.py`/`test_regression.py`).
- **What:** `_maybe_graph_model` gated capture on **only** the global capability check `cuda_graph_enabled()` (autodetect-ON for any sm_80+ host — the RTX 5080 is sm_120) and never on the trainer's *own* `self.device`. Many unit/integration tests (and any `FF_DEVICE=cpu` run on a GPU box) construct `MultiHeadTrainer(..., device=torch.device("cpu"))`. On a CUDA host those CPU-device trainers still entered the guard and called `torch.cuda.make_graphed_callables` on a **CPU** model → captured garbage → `NaN` MAE ("no valid checkpoint saved (all epochs had NaN MAE)") / non-decreasing train loss. Green on CPU/CI (where `cuda_graph_enabled()` is False) and in single-process local runs, red under the default `-n auto` GPU run → read as a "K NN test flake" (#690, which had been triaged `leave` as "K's nested trainer no-ops capture" — that closed the K *crash* but not this base-trainer flake). The base `MultiHeadTrainer` was the actual culprit, so it hit all six positions, not just K.
- **Fix:** Added `self.device.type != "cuda"` to the early-return: `if self._graphed or self.device.type != "cuda" or not cuda_graph_enabled(): return`. Mirrors the two existing per-trainer device gates — the AMP gate in `__init__` (`getattr(device, "type", None) == "cuda"`, ~L652) and the `_cuda` guard in `train()` (~L837). **Numerically inert on production:** Batch trains on CUDA (g6/L4 sm_89) where `self.device.type == "cuda"`, so the new clause is False and control flow is byte-identical → no benchmark move, no graphed-vs-graphed rebaseline. Verified: K NN tests 47 passed ×3 under xdist (was 2 failed ×3); `tests/shared/test_cuda_graph.py` 28 passed (real capture still exercised); `pytest -m unit` 2535 passed on the 5080.
- **Lesson:** A *global* capability check (`cuda_graph_enabled()`, `amp_dtype()`, `_gpu_resident_device()`) is not the same as the *caller's intended device*. Anything that engages a CUDA-only fast path must also confirm the consumer is actually on CUDA — the trainer knows its `self.device`; use it. **Related (separate mechanism, fixed in the follow-up entry below):** `make_dataloaders` / `make_history_dataloaders` make the *same* mistake via `_gpu_resident_device()` — a CPU-device trainer on a GPU box gets GPU-resident, non-bit-identical, unseeded-shuffle loaders, which flakes the `@pytest.mark.integration` regression tests (qb/rb/wr/dst: NN MAE 60–100 vs LGBM 5–15, varying run-to-run; passes with `FF_DEVICE=cpu`). That path is graph-independent (reproduces with `FF_CUDA_GRAPH=0`), CI-safe (CPU), and was *not* fixed in this PR — the dataloader factory doesn't receive the device. Fixed in the follow-up by making residency opt-in (see next entry).
