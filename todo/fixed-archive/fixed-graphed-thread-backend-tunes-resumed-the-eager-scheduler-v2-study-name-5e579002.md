### [FIXED] Graphed thread-backend tunes resumed the eager `scheduler_v2` study (namespace 2×2 blind spot)
- **File(s):** [../src/tuning/tune_nn_storage.py](../../src/tuning/tune_nn_storage.py) (`GRAPH_SEARCH_SPACE_VERSION` + thread branch of `resolve_search_space_version`); test in [../tests/tuning/test_tune_nn.py](../../tests/tuning/test_tune_nn.py).
- **What:** `resolve_search_space_version` only honored `cuda_graph` for the mps backend; the thread branch always returned the eager `scheduler_v2`. Since the 2026-06-05 CUDA-graph autodetect cutover, sm_80+ boxes train **graphed by default**, so any thread-backend tune there resumed and extended the eager study — mixing training regimes the namespace machinery exists to keep apart (graphed runs compare to graphed runs, ADR-0017). Found while designing a thread-vs-MPS backend A/B whose thread arm would have polluted the local study.
- **Fix:** `scheduler_v2_graph` for thread+graph, completing the 2×2 backend×graph matrix; mps namespaces unchanged. Residual (chip filed): `tune_nn.main` derives `cuda_graph` from `_env_truthy("FF_CUDA_GRAPH")`, which mislabels autodetect-ON local runs (env unset) and sm<80 boxes with the env force-set — should resolve via `cuda_graph_enabled()`. The Batch path is unaffected (launch_tune always sets the env explicitly).
- **Lesson:** When a namespace/versioning scheme is keyed on an execution mode, enumerate the FULL mode matrix at design time — a "backend implies mode" shortcut (thread⇒local⇒eager) silently breaks when a later change (autodetect-ON graphs) decouples the modes. And label state by the *resolved* decision (`cuda_graph_enabled()`), not the raw env input that feeds it.
