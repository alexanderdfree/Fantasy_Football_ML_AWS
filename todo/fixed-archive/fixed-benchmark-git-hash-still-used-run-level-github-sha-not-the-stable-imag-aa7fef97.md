### [FIXED] Benchmark `git_hash` still used run-level `$GITHUB_SHA`, not the stable image SHA (audit-320 F40/F41)
- **File(s):** `.github/workflows/train-batch.yml`, `.github/workflows/train-ec2.yml` (`--git-hash "$GITHUB_SHA"` → `--git-hash "$HEAD_SHA"`, where `$HEAD_SHA = ${{ github.event.workflow_run.head_sha }}`; the auto-run `--note` SHA switched to the same `$HEAD_SHA`).
- **What:** The "[FIXED] Benchmark `git_hash` recorded the wrong SHA" entry (immediately below) fixed the *workspace-HEAD* bug but landed on `--git-hash "$GITHUB_SHA"` and asserted "for `workflow_run` events that's `workflow_run.head_sha`." That assertion is **wrong**: on a `workflow_run` trigger `github.sha`/`$GITHUB_SHA` is the *run-level* head_sha (current `main` HEAD when the downstream run was queued), which diverges from `github.event.workflow_run.head_sha` (the stable upstream image-build SHA) on rapid back-to-back merges — the exact two-head_sha trap the dedup-fix entry (`switch train-batch dedup to S3 marker keyed by workflow_run.head_sha`, PR #310) later documented. So the benchmark `git_hash` (and note SHA) could still mislabel a row whenever `main` advanced between the upstream image build and the downstream train run.
- **Fix:** Pin both the structured `git_hash` and the auto-run note to `$HEAD_SHA` (`workflow_run.head_sha`) — the same stable identifier the dedup marker (`train-success-markers/${HEAD_SHA}.txt`), the job-def-revision pin (`job-def-revisions/${HEAD_SHA}.txt`), `FF_TRAIN_GIT_SHA`, and the concurrency group already use. Every SHA the train workflow records is now the image-build SHA — coherent across dedup / provenance / benchmark.
- **Lesson:** When one part of a `workflow_run` workflow switches to `workflow_run.head_sha`, grep the WHOLE workflow for other consumers of `$GITHUB_SHA` that assume the two head_shas coincide — they don't on rapid merges. The benchmark `git_hash` was the straggler the dedup fix didn't carry over.
