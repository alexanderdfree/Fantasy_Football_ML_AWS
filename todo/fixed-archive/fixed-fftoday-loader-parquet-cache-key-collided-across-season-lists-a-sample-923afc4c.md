### [FIXED] FFToday loader parquet-cache key collided across season lists — a sampled pull silently served a later full-range request
- **File(s):** [../src/analysis/fftoday_loader.py](../../src/analysis/fftoday_loader.py) (`_seasons_sig`, `_CACHE_VERSION` v1→v2), [../tests/analysis/test_fftoday_loader.py](../../tests/analysis/test_fftoday_loader.py) (`test_cache_key_distinguishes_sampled_from_contiguous_seasons`), commit `3a643e6` (expert-edge Phase-1 PR).
- **What:** `load_fftoday_projections` / `load_fftoday_with_gsis_id` keyed their parquet caches on `{min(seasons)}_{max(seasons)}` only, while the sibling `weeks_sig` already disambiguated non-contiguous week tuples. A sampled `[2013, 2019, 2024]` vet pull wrote `fftoday_projections_v1_2013_2024_w1-18.parquet`, and a later `[2013..2024]` full-archive request cache-hit that exact filename — returning 3 seasons as if they were 12, no error. Caught during the 2026-07-06 backfill vet only because the per-season verdict table printed 3 season keys instead of 12.
- **Fix:** `_seasons_sig()` mirrors the `weeks_sig` pattern (`{lo}_{hi}` when contiguous, `{lo}_{hi}-n{count}` otherwise) in both cache paths, and `_CACHE_VERSION` bumped to v2 so legacy ambiguous cache files are orphaned rather than re-read (the new naming alone would still have collided with the already-written v1 file). Regression test pins that a contiguous request re-fetches instead of consuming the sampled cache.
- **Lesson:** a cache key must encode the **full request identity**, not the endpoints of a range — min/max compresses a *list* into a *span* and every distinct subset of that span collides. When a loader has two request axes (seasons × weeks) and only one carries a disambiguator, the other is a latent silent-wrong-data bug; grep the file for every `min(`/`max(`-keyed cache path and fix them together. Version-bump on key-format change, else old ambiguous files keep matching the new "contiguous" spelling.
