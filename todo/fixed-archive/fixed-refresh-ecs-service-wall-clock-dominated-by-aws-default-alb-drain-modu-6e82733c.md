### [FIXED] "Refresh ECS service" wall-clock dominated by AWS-default ALB drain + module-level S3 sync under `--preload`
- **Files:** `.github/workflows/deploy.yml` (new "Tune ALB target group for fast rolling deploys" step before "Deploy to ECS"; resolves target-group ARN via `aws ecs describe-services` then issues `aws elbv2 modify-target-group-attributes` + `aws elbv2 modify-target-group`), `gunicorn.conf.py` (new `on_starting(server)` hook owns the four boot-time S3 syncs), `src/serving/app.py` (deleted four module-level `sync_*_from_s3()` calls + their imports — only `upload_predictions_cache_to_s3` import remains because it's used at line 1371). Wall-clock claims in `CLAUDE.md`, `docs/batch_design.md`, `infra/batch/README.md` updated from the 2026-05-20 design estimate (~25–30 min full train job) to the 2026-05-21 measured value (~15 min: ~10 min "Submit Batch jobs and wait" + ~3 min "Refresh ECS service" after this fix; ~8 min before). ADR `Update history` entry added in `docs/ARCHITECTURE.md` extending D14.
- **What:** Both deploy paths' "Refresh ECS service" / "Deploy to ECS" steps were consistently 8–11 min — much longer than the actual work being done. Three serial costs stacked: (a) the ALB target group's default `deregistration_delay.timeout_seconds=300` waited 5 min for the OLD task to drain on every rolling redeploy, regardless of whether any in-flight requests existed (Flask request p99 ≪ 1 s — the 300 s default exists for stateful long-poll services this app isn't); (b) `HealthyThresholdCount=5` × `HealthCheckIntervalSeconds=30` = 150 s of ALB checks before a fresh task was marked healthy; (c) `src/serving/app.py:83–86` invoked `sync_data_from_s3()`, `sync_models_from_s3()`, `sync_benchmark_history_from_s3()`, `sync_predictions_cache_from_s3()` at module-import time, which runs *before* `bind()` under `gunicorn --preload` — exactly the failure mode the predecessor PRs #148/#149 documented (entry: "Gunicorn `--preload` pre-warm broke ALB health checks"). The first-request cold-start fix that introduced D14 ("First-request cold start" entry below) added `post_fork` for the prediction warm but left the S3 sync at module level, so the rule had not been fully applied.
- **Fix:** Three combined moves. (1) **F1** — `deregistration_delay.timeout_seconds=30` (was 300), shaving ~270 s off every rolling redeploy. (2) **F3** — `HealthyThresholdCount=2`, `HealthCheckIntervalSeconds=10`, shaving ~130 s off the new-task half. Both applied idempotently from `deploy.yml` before the "Deploy to ECS" step so the about-to-drain task uses the new value; target-group ARN is discovered from the service so the step stays in sync with whatever target group the service is attached to. (3) **F2** — moved the four `sync_*_from_s3()` calls into a new `on_starting(server)` hook in `gunicorn.conf.py` so `src.serving.app` is side-effect-free at import. Wall-clock unchanged by F2 alone (both pre-`bind` and post-import run before workers start dispatching), but the import-time side effects that previously sat one line away from "just adding another sync" are gone, and the gunicorn config now reflects the architectural rule it documents. **F4** (skip data parquets at serving boot) was investigated and dropped — `_load_base_data_locked` at `src/serving/app.py:1026–1028` reads all three splits to populate the test-set predictions table that the UI surfaces, and the predictions-cache fingerprint at `src/serving/app.py:1257` walks the same files; dropping them would break both. Raw parquets are also load-bearing (K reconstructs kicker stats; all positions read schedules for weather features).
- **Lesson:** "AWS defaults are reasonable" is a heuristic, not a fact — `deregistration_delay.timeout_seconds=300` is right for stateful long-poll services and wrong for everything else, and rolling redeploys cost ~270 s every time until the operator notices and tunes it. The PR #148/#149 rule ("no module-level pre-warm under `--preload`") is correct but applying it only to the *prediction* warm (D14) and not to the S3 *sync* itself was a partial application — the next person reading `src/serving/app.py:83` had no signal that the four innocuous-looking calls at module top were on the exact slope D14 was meant to prevent. When a rule has a structural form ("no module-level X under `--preload`"), apply it to every X, not just the X that triggered the original incident. Operationally, "the deploy is slow" is almost always two or three serial costs stacking — bisecting the steps' wall-clock with `gh run view --json jobs` lands the right fix faster than guessing.
