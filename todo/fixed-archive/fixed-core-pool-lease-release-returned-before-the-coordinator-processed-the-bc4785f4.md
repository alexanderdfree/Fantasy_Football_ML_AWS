### [FIXED] core_pool lease release returned before the coordinator processed the release
- **File(s):** [src/shared/core_pool.py](../../src/shared/core_pool.py) (`release` now sends a coordinator ack; `lease_cores` waits for it before returning from the context manager).
- **What:** The full `pytest -m unit -q` xdist run repeatedly failed `tests/shared/test_core_pool.py::test_coordinator_grant_release_roundtrip`: after a first lease exited and `active_count` dropped from 2 to 1, the next lease sometimes received only 2 cores instead of all 4. The test passed in isolation because the coordinator usually processed the async `release` before the next acquire; under full-suite load, the client returned from `lease_cores().__exit__` immediately after `sendall({"op":"release"})`, before the server thread had necessarily returned the cores to the allocator.
- **Fix:** Make release synchronous: the coordinator writes a `{"released": true}` ack after releasing and notifying waiters, and the client waits briefly for that ack before closing the socket. Abrupt-disconnect reclamation remains intact because a client that closes without reading the ack still reaches the idempotent `finally` release path.
- **Lesson:** A context manager that claims a distributed/socket-backed resource is released on exit must wait for the owner to acknowledge the release before returning. `sendall()` only proves bytes were queued locally; it does not prove the coordinator processed them. Tests that pass in isolation but fail only under xdist can expose these ordering races.
