### [REMOVED] SOCI lazy-loading never worked on AWS Batch (ECS-EC2 unsupported)
- **File(s):** `infra/batch/userdata.sh` (deleted), [../infra/batch/setup.sh](../../infra/batch/setup.sh) (launch-template machinery removed; the `instanceTypes` reconcile from the adjacent g4dn→g6 fix is preserved), [../.github/workflows/batch-image.yml](../../.github/workflows/batch-image.yml) ("Publish SOCI index" step removed), [../docs/batch_design.md](../../docs/batch_design.md) §2a + [../infra/batch/README.md](../../infra/batch/README.md) (claims corrected). Investigated/validated on live AL2023 ECS GPU hosts (containerd 2.2.1), 2026-06-07.
- **What:** The Batch cold-start optimization claimed SOCI lazy-loading cut the image pull ~122s → ~5–10s (total cold-start ~258s → ~135s). It **never fired**: live ECS task pull windows measured ~118–122s. Two layers of failure: (1) `userdata.sh` only registered the `[proxy_plugins.soci]` proxy plugin but never *selected* soci as the snapshotter (containerd 2.x **transfer-service** `unpack_config`), gave the daemon **no ECR credentials**, or enabled the `soci_v1` pull mode; (2) more fundamentally, AWS Batch runs on **ECS-managed EC2**, and the **amazon-ecs-agent does not pull through the soci snapshotter** — SOCI on ECS is **Fargate-only** ([aws/containers-roadmap#1832](https://github.com/aws/containers-roadmap/issues/1832), open since 2022). Fargate has no GPU, so GPU training (→ must be EC2 → ECS agent) can never use it — and this is the ECS agent's limitation, **not** the GPU arch, so the just-completed g4dn→g6 migration (adjacent entry) does **not** unblock it.
- **Evidence:** Fixed all three userdata gaps and *validated lazy-load works for a `ctr` pull* on a fresh AL2023 host (7s / 9 KiB transferred / 8 FUSE mounts / `remote-snapshot-prepared:true`). But a prod K smoke test on a (g4dn-at-the-time) host with that exact config still pulled in **103s** (overlayfs) — the ECS agent ignored the snapshotter config. The ECR index is fine (referrers API returns it, subject = image digest) and the job def correctly pins the indexed `:$sha`; the gap is purely the ECS-agent pull path.
- **Fix:** Removed the SOCI machinery (userdata launch template, CI index publish, `setup.sh` LT plumbing). Cold-start returns to the ~120s full pull it always actually was (no regression — the SOCI path was inert). Mid-investigation, an attempted LT detach also surfaced a footgun: the README's documented `launchTemplate={}` detach is rejected by AWS, and chaining a `delete-launch-template` past that failed gate left the CE pointing at a deleted template — recovered by recreating `ff-batch-lt` as a no-op (AWS Batch can't drop a launch-template *reference* from an existing CE without recreating it). Cold-start levers that DO work on GPU/EC2: a **warm pre-pulled instance** (no pull at all) or shrinking the 3.8 GB image.
- **Lesson:** SOCI lazy-loading is a **Fargate** feature; the ECS-EC2 `amazon-ecs-agent` does not use the soci snapshotter regardless of containerd config **or GPU arch**. A containerd-level fix that works for `ctr`/CRI does **NOT** imply the ECS agent uses it — verify a cold-start optimization with the **actual ECS task pull window** (`describe-tasks` `pullStartedAt`/`pullStoppedAt`), not a `ctr` proxy. And never chain a destructive `delete` past an unverified `update` gate. Don't re-attempt SOCI on the Batch path unless AWS ships #1832.
