### [FIXED] Serving OOM-loop after a splits refresh — in-container prediction-cache recompute OOMs the 2-worker task; moved to a CI build + 8 GB
- **File(s):** [../src/scripts/build_serving_cache.py](../../src/scripts/build_serving_cache.py) (new off-container builder), [../.github/workflows/refresh-splits.yml](../../.github/workflows/refresh-splits.yml) (build+upload cache before the ECS roll), [../infra/aws/task-definition.json](../../infra/aws/task-definition.json) (`memory` 4096→8192) + [../.github/workflows/deploy.yml](../../.github/workflows/deploy.yml) (pin cpu/memory from that file), ADR-0014 changelog.
- **What:** `/api/predictions?position=ALL` + `/api/snapshot` went 502/404 (Season Leaders / Model Performance down; single-position lazy loads still 200). The serving prediction-cache fingerprint is a content-hash over `data/splits/*` + `data/raw/*` + models, all S3-synced at boot. A scheduled `refresh-splits` rewrote `data/splits/*` in S3 (23:40) → fingerprint drifted `fc6a4258`→`a8cb2fd0` → the 20:12 cache no longer matched. `refresh-splits` then force-rolls the ECS service (so tasks pick up new splits); the fresh tasks found no hydratable cache and **both gunicorn `--workers 2` post_fork threads recomputed the full 6-position pipeline concurrently → ~2× peak memory → exceeded the 4 GB task → OOM-kill loop** (3 SIGKILLs/30s, not self-healing). A serving-only "no-op" deploy ([#1158]) also triggers it by rolling the in-memory-cache tasks. Memory was ~76–88% steady; the recompute's extra peak ×2 workers tipped it. NB: this recompute is NOT the unfixable upcoming-week build (ADR-0018) — it had succeeded once in 4 GB; concurrency tipped it.
- **Fix:** Build the cache **off-container** (ADR-0018 pattern, already used for the upcoming-week artifact): `build_serving_cache.py` syncs the same S3 splits/raw/models, runs `_ensure_metrics`, validates row/position coverage, and uploads — so the fingerprint matches by construction and serving **hydrates** (never recomputes). `refresh-splits.yml` runs it right **before** the ECS roll, so rolled tasks hydrate the fresh cache. Safety net: serving task → 8 GB (`deploy.yml` now pins cpu/memory from `infra/aws/task-definition.json`, which it previously ignored — it inherited the live revision), so any cold-boot/retrain recompute still fits. Immediate restore: ran `build_serving_cache.py` once by hand (fp `a8cb2fd0`, 7177 rows, nflcom 6597) → `force-new-deployment` → tasks hydrated → restored.
- **Lesson:** Anything that rewrites a fingerprinted S3 input (splits/raw via `refresh-splits`) must also refresh the artifact that fingerprint gates — don't leave the serving container to rebuild a heavy artifact in-process; the 2-worker task can't host two concurrent 6-position recomputes. The serving fingerprint keys on S3-synced data, so an off-container build that syncs the same S3 state matches it deterministically (no race). A "no-op" serving deploy is NOT no-op when it rolls tasks that must rebuild a cold cache. `deploy.yml` re-registered the *live* task def, so capacity changes must be applied to the live revision (or sourced from the repo file), not just edited in the placeholder `task-definition.json`.
