### [FIXED] refresh-splits.yml verify-before-publish ordering → train-batch fail-safe trained on STALE splits
- **File(s):** [../.github/workflows/refresh-splits.yml](../../.github/workflows/refresh-splits.yml) (step order); guarded by [../tests/test_refresh_splits_workflow.py](../../tests/test_refresh_splits_workflow.py).
- **What:** refresh-splits ran two slow **warn-only diagnostics** — "Verify train→test covariate shift" + "Verify depth-chart temporal alignment" — BEFORE "Upload to S3" + "Mark splits-rebuild ready". On a cold-cache run the ~14.5-min regen + the ~15-min covariate diagnostic pushed the ready marker past train-batch's ~20-min fail-safe wait, so train-batch proceeded on the EXISTING (stale) S3 splits and CANCELLED the orphaned refresh-splits — the freshly-built splits were never published. Silent: the refresh run shows `cancelled`, the splits actually regenerated fine (step 8 ✓), and the model just trains a commit behind. First caught on the #1051 (`4b76fb2`) retrain. Would also mask any Tier-C split-build metric-mover as a **false Δ0**.
- **Fix:** Reorder — Upload-artifact / Upload-S3 / Confirm-S3 / Mark-ready now run right after the *fast* "Verify engineered columns present" gate; the two slow diagnostics moved to AFTER "Mark ready" as post-publish checks (set `COVSHIFT_HARD_FAIL`/`DEPTH_ALIGN_HARD_FAIL=1` for a post-publish hard alert — they no longer gate the upload). Marker now lands ~1 min after regen+upload, well inside the fail-safe window. Column-presence gate still precedes the upload (8c46b59 protection intact); ready-after-upload + ECS-after-upload invariants preserved (all 9 workflow tests pass).
- **Lesson:** A slow, *non-gating* diagnostic placed before the publish step still blocks everything downstream — including a race-gate marker another workflow waits on. Publish + signal "ready" as early as the essential gates allow; run optional diagnostics after. "Warn-only" ≠ "non-blocking" if it sits in the critical path.
