### [FIXED] `[docs-only]` substring-match false-positived on commits that *described* the feature
- **Files:** [.github/workflows/batch-image.yml](../../.github/workflows/batch-image.yml) (moved the workflow-expression `if: "!contains(...)"` into a leading `check-docs-only` shell job — workflow expressions can't do regex/awk), [.github/workflows/_detect-positions.yml](../../.github/workflows/_detect-positions.yml) (awk-filtered `grep -qF`), [.github/workflows/tests.yml](../../.github/workflows/tests.yml) (per-commit subject loop over `BASE..HEAD`), [.claude/hooks/pre-pr.sh](../../.claude/hooks/pre-pr.sh) (new `docs_only_in_range()` helper used at the early-bail check and B2 metric-regression check), [CLAUDE.md](../../CLAUDE.md) ("commit-message opt-in" → "commit-subject opt-in" + explicit prose-mentions-don't-count note + cross-link to this archive entry).
- **What:** All four consumers of the `[docs-only]` opt-in tag did a flat substring match against the *entire* commit message (`!contains(head_commit.message, '[docs-only]')` in batch-image; `git log ... --format=%B | grep -qF '[docs-only]'` in the others). The substring fired on prose mentions in commit bodies, not just on the opt-in tag in commit subjects. Two confirmed victims on the 2026-05-21 sweep:
  (1) The PR that *added* the `[docs-only]` feature itself, commit `6d0490e2` — its title contains the literal `[docs-only]` describing what the PR does, matched by its own gate at merge, so the merge that introduced the feature skipped its own image rebuild.
  (2) PR [#293](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/293) (`e802a47`) — a BF16 perf change. A constituent commit (`ci(pre-pr): recognize {pos}/outputs/models freshness`) wrote in its body: *"Per-position file changes still require *that* position's evidence — that branch is unchanged. The ``[docs-only]`` opt-in now also clears ``shared_changed``..."*. Squash-merge body carried this prose into `head_commit.message`; the substring match fired; batch-image.yml's `build-and-push` job skipped; no new image was pushed. The next post-merge Batch run trained against the previous image (FP32), so `benchmark_history/`'s entry for `e802a47` is the FP32 baseline, not BF16. The actual BF16 measurement only landed when PR [#295](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/295) (`d1b7457`, touches `infra/batch/**` → batch-image.yml ran normally) rebuilt the image — that run carries the BF16 measurement but attributes it to #295's commit, not #293's. Net effect: a perf change shipped without a verifiable benchmark for several merge cycles.
- **Fix:** Restrict the match to *subject lines* via an awk filter `awk 'NR==1 || /^\* /'` — keeps line 1 (squash-merge subject or direct-push subject) and any `^\* `-prefixed line (squash-merge constituent commit subjects), drops everything else. The four consumers each pipe `git log --format=%B` through that filter before `grep -qF '[docs-only]'`. For tests.yml + pre-pr.sh, which scan a multi-commit range, iterate per-commit (`for sha in $(git log --format=%H "$range"); do ...`) rather than catting the range — `git log --format=%B` puts no separator between commits, so a body line of commit N+1 would otherwise look like a subject of commit N. For batch-image.yml, the workflow expression `if:` can't run awk, so the check moved into a leading `check-docs-only` job whose output gates `build-and-push`; workflow_dispatch bypasses the check (operator-driven re-build always proceeds). Fixture-tested locally with 4 mock commits — the e802a47-shape body-only-prose commit now correctly evaluates to `docs_only=false`, while the legitimate-tag cases (PR title or `* [docs-only]` constituent subject) still evaluate to `true`. Verification of the recurrence: this PR itself updates [CLAUDE.md](../../CLAUDE.md) to *describe* the `[docs-only]` feature; with the old substring check, this PR would have skipped its own image rebuild. The new subject-line filter correctly evaluates this PR's commit subject (a `fix(ci):` subject) as `docs_only=false`.
- **Lesson:** When a sentinel substring serves as a control-plane signal in commit messages, the matcher needs to distinguish "the author tagged this commit" from "the author talked about the tag." `[docs-only]` in `* [docs-only] fix typo` (constituent subject) IS the signal; `[docs-only]` in `the [docs-only] opt-in now also clears X` (prose) IS NOT. Restricting the match to *where authors put control signals* (subject lines, not body prose) handles both squash-merge formats and prevents the meta-bug where any commit that updates the matcher itself triggers its own skip. Companion lesson on dogfooding: a CI control-signal that fires on prose mentions makes the feature uneditable — the next PR that touches `[docs-only]`-handling code, even to fix a bug in it, will dogfood-skip the workflows it just modified, masking whether the fix actually works. Subject-line scoping is the structural fix; "don't mention the feature in commit messages" was the working-around-it fix the matcher's flaw forced on authors. Operationally: when a workflow expression's matcher needs more than `contains()`/`startsWith()`/`endsWith()`, the fix is almost always "move it to a shell-backed leading job whose output gates the real job" — workflow expressions are intentionally underpowered.
