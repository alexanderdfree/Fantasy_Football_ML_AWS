### [FIXED] Batch Spot queue stuck on g6-only capacity during us-east-1 g6 shortage
- **File(s):** [../infra/batch/setup.sh](../../infra/batch/setup.sh) (primary/fallback CE provisioning + queue-order reconcile), live AWS Batch `ff-training-queue` / `ff-gpu-spot` / `ff-gpu-spot-g5`, [../src/batch/benchmark.py](../../src/batch/benchmark.py) (A10G/g5 and mixed-GPU labels), [../src/tuning/tune_nn.py](../../src/tuning/tune_nn.py) (A10G Batch MPS auto profile), [../docs/adr/0013-spot-fan-out-via-aws-batch.md](../../docs/adr/0013-spot-fan-out-via-aws-batch.md), [../docs/adr/0017-platform-autodetection-per-arch-optimization-policy.md](../../docs/adr/0017-platform-autodetection-per-arch-optimization-policy.md), [../AGENTS.md](../../AGENTS.md).
- **What:** On 2026-06-08, `ff-training-queue` sat at 11 `RUNNABLE`, 0 `RUNNING`, while `ff-gpu-spot` was healthy but could not launch `g6.xlarge` Spot capacity: Auto Scaling repeatedly reported `UnfulfillableCapacity`, recent attempts ended with `Server.SpotInstanceTermination`, and ECS had 0 registered instances. The account's G/VT Spot quota was not the blocker (live quota 64 vCPU); the CE was simply pinned to one exhausted Spot pool. A first-cut mixed `instanceTypes=["g6.xlarge","g5.xlarge"]` CE would have improved capacity but would not guarantee g6 preference because `SPOT_PRICE_CAPACITY_OPTIMIZED` can select any pool inside a CE.
- **Fix:** Preserve g6 preference with two ordered compute environments instead of one mixed CE: `ff-gpu-spot` remains `g6.xlarge` at job-queue `order=1`; `ff-gpu-spot-g5` is a new `g5.xlarge` fallback at `order=2`. `setup.sh` now creates/reconciles both CEs, resolves subnets per instance type, and updates the job queue order idempotently. Live recovery required temporarily disabling the g6 CE after Batch kept hammering the valid-but-unfulfillable primary; that forced the current backlog onto g5, then g6 was re-enabled so future placements prefer it. Verification: queue order correct, both CEs `ENABLED`/`VALID`, g5 desired capacity rose and the queue started draining (`RUNNABLE` 11→10, one WR job `STARTING`).
- **Lesson:** For AWS Batch Spot, "add another instance type" and "prefer this instance type" are different mechanisms. A mixed instance-type CE gives Batch more pools but not a hard preference; compute-environment order is the preference mechanism. If the ordered primary is valid but currently unfulfillable, Batch may keep retrying it instead of immediately falling through — a temporary primary-CE disable can be the live-drain lever, but re-enable it once fallback capacity is requested so the durable policy remains g6-first.
- **[SUPERSEDED 2026-06-22]:** The two-ordered-CE design above never delivered capacity fallback in practice and was reverted. A job queue's compute-environment *order* only advances to the next CE on a **misconfiguration** (`maxvCpus` / job resource req / unsupported config / service role) — **never** on Spot capacity starvation. So a healthy, below-`maxvCpus` `ff-gpu-spot` (g6-only) that simply couldn't get g6 Spot parked all jobs in `RUNNABLE` and never reached `ff-gpu-spot-g5` behind it (recurred 2026-06-22: six NN jobs stuck `RUNNABLE`, 0 instances). Fix: fold g5 into one diversified CE — `ff-gpu-spot` now lists `instanceTypes=["g6.xlarge","g5.xlarge"]` under `SPOT_PRICE_CAPACITY_OPTIMIZED` (capacity fallback is the allocation strategy *inside* a CE, not queue order; mirrors `ff-cpu-spot`'s c8a+m8a); `ff-gpu-spot-g5` dropped from the queue order and disabled. The "durable policy remains g6-first" lesson above is **obsolete** — g6/g5 are now one pool with no strict preference (both sm_80+, metric-identical), and the live fix flipped the stuck jobs `RUNNABLE → STARTING → SUCCEEDED`. See [../docs/adr/0013-spot-fan-out-via-aws-batch.md](../../docs/adr/0013-spot-fan-out-via-aws-batch.md) (2026-06-22 changelog). **Lesson:** for AWS Batch Spot, an ordered fallback CE rescues you from "primary full/broken," not from "primary can't get Spot" — diversify `instanceTypes` within ONE CE for capacity fallback.
