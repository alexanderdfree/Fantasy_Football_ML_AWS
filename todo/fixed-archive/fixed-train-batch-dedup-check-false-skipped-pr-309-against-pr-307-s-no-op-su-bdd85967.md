### [FIXED] train-batch dedup_check false-skipped PR #309 against PR #307's no-op success run
- **File(s):** [.github/workflows/train-batch.yml](../../.github/workflows/train-batch.yml) (`dedup_check` job's `gh run list --commit "$HEAD_SHA"` query replaced with `aws s3api head-object` against `s3://ff-predictor-training/train-success-markers/${HEAD_SHA}.txt`; added `aws-actions/configure-aws-credentials@v4` step reusing the same secrets the `train` job already binds; `permissions:` lost the no-longer-needed `actions: read`; env lost `GH_TOKEN`/`RUN_ID`/`REPO`. New `Write train-success marker for dedup` step in the `train` job uploads the marker after artifact-freshness verification and before benchmark commit — only writes on genuine train success, not positions=empty no-ops).
- **What:** On 2026-05-21 11:13:24Z, train-batch run #71 (`26222475745`) — triggered by PR #309's batch-image build (workflow_run.head_sha=`04ef622`) — was deduped against run #69 (`26222253006`, conclusion=success) and its `train` job was skipped. PR #309's "GPU-resident dataset path" perf change shipped to ECR but never trained on Batch; production stayed on the prior image's model. Run #69's own train was also skipped — but for a *different* reason: at 11:08:31Z it was triggered by PR #307's batch-image build (workflow_run.head_sha=`189c568`), checked out 189c568 ("BLAS-thread cap"), found only `infra/batch/*.json` in `git diff HEAD^ HEAD` (not model-relevant per `scope_positions.py`), and exited with `positions=""` → train skipped, run conclusion=`success`. Two compounding bugs surfaced in sequence:
  (1) **Identifier mismatch.** GitHub Actions exposes two distinct `head_sha` values on a workflow_run-triggered run — the event-payload `workflow_run.head_sha` (stable per upstream run, accessible as `${{ github.event.workflow_run.head_sha }}`, = `189c568` for run #69) and the run-LEVEL `head_sha` (= current main HEAD when the downstream run was queued, accessible via `gh api .../actions/runs/{id}.head_sha`, = `04ef622` for run #69 because PR #309 had already merged at 11:06:09Z before the workflow_run event fired at 11:08:31Z). `gh run list --commit <SHA>` filters by the **run-level** head_sha; the dedup query passed the **workflow_run** head_sha. On rapid back-to-back merges these two diverge for the same run. Run #71's query `gh run list --commit 04ef622` returned run #69 (run-level head_sha matched) even though run #69 actually corresponded to PR #307's image build. False positive.
  (2) **"Successful" was too broad.** Run #69's conclusion=`success` even though its train was skipped via positions=empty; the dedup_check counted any successful train-batch run, including no-ops where no training actually happened.
- **Fix:** Two-part change to [.github/workflows/train-batch.yml](../../.github/workflows/train-batch.yml). (a) **Switch the dedup-key mechanism**: replace `gh run list --commit "$HEAD_SHA"` with `aws s3api head-object --key "train-success-markers/${HEAD_SHA}.txt"`, where the marker is keyed by `${{ github.event.workflow_run.head_sha }}` — the same identifier as the working `job-def-revisions/${HEAD_SHA}.txt` pin from D13's layer-A race fix (writer in [batch-image.yml](../../.github/workflows/batch-image.yml) keys by `$GITHUB_SHA`, reader in train-batch keys by `workflow_run.head_sha`; both equal the upstream's SHA, so they can't drift). dedup_check adds an `aws-actions/configure-aws-credentials@v4` step reusing the same `secrets.AWS_ACCESS_KEY_ID` / `secrets.AWS_SECRET_ACCESS_KEY` the `train` job already binds — no new credentials are introduced. (b) **Tighten what counts as a "successful train"**: add a new `Write train-success marker for dedup` step in the `train` job between artifact-freshness verification and benchmark commit — uploads `s3://ff-predictor-training/train-success-markers/${HEAD_SHA}.txt` with body=`${GITHUB_RUN_ID}`. Step placement is load-bearing: AFTER freshness (so we never mark a positions=empty no-op or a stale-artifact success), BEFORE benchmark commit (so a transient `git push` failure on `benchmark_history/` still leaves the marker — re-runs hit the benchmark-only path, not a full retrain). `workflow_dispatch` keeps bypassing dedup; the marker step is gated by `if: github.event_name != 'workflow_dispatch'` so manual dispatches don't pollute the marker space. The `_detect-positions.yml` checkout at `workflow_run.head_sha` is correct as-is — it diffs the right commit; the bug was purely in dedup_check's query mechanism. PR #309's training itself is a separate backfill (manual `gh workflow run train-batch.yml -f positions="QB RB WR TE K DST"` or `gh workflow run batch-image.yml --ref 04ef622` for precise bench attribution); the workflow fix unblocks future runs but doesn't retroactively train #309.
- **Lesson:** GitHub Actions exposes TWO `head_sha` fields on workflow_run-triggered runs — the event-payload `workflow_run.head_sha` (= the SHA the upstream ran against, stable) and the run-level `head_sha` (= current main HEAD when queued, race-prone). They coincide when main hasn't advanced between upstream completion and downstream queue, and diverge on rapid back-to-back merges. `gh run list --commit` filters by the latter; `${{ github.event.workflow_run.head_sha }}` reads the former. **Never use them interchangeably**, especially as dedup keys. Companion structural lesson: dedup-key mechanisms in CI workflows should mirror the writer's identifier exactly — the existing `job-def-revisions/${HEAD_SHA}.txt` pattern from the layer-A race fix already used `workflow_run.head_sha` on both sides and didn't drift; the dedup_check from PR #299 used `workflow_run.head_sha` on the read side but the run-level `head_sha` (via `--commit`) on the implicit write side, and that mismatch was the bug. Companion lesson on diagnostic interpretation: a workflow's overall `conclusion: success` doesn't imply the gated job actually ran — the dedup_check should only mark "trained" runs as successful, not any-job-passed runs. Marker-based dedup gets this right by construction (write step lives in the gated job); query-based dedup over `gh run list --status=success` needs a tighter predicate.
