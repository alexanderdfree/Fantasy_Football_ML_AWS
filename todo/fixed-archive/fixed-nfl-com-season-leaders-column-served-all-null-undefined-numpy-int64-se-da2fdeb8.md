### [FIXED] NFL.com Season Leaders column served all-null ("undefined") — numpy.int64 seasons rejected by nflreadpy's strict `isinstance(season, int)`
- **File(s):** [../src/serving/core.py](../../src/serving/core.py) (`_historical_expert_seasons` now returns native `int`; `_PREDICTIONS_CACHE_SCHEMA_VERSION` 5→6 to force a one-time recompute), regression test in [../tests/test_app_expert_predictions.py](../../tests/test_app_expert_predictions.py).
- **What:** Every `nflcom_pred*` value in the served predictions cache (Season Leaders / predictions tab) was null — rendered "--"/undefined for all 7177 rows — while RotoWire, Ridge, NN, LGBM populated normally. The served 2025 S3 cache (built 2026-06-13) confirmed it (`nflcom` 0/7177, `rotowire` 6009/7177). Production logs pinned the exact error: `[experts] NFL.com projections unavailable: ValueError('Season must be between 1920 and 2026')` — misleading, because 2025 *is* in range. Root cause: `_historical_expert_seasons` returned `sorted(seasons.astype(int).unique())` = a list of **numpy.int64**, handed to `load_nflcom_with_gsis_id` → `nfl_source.rosters` → nflreadpy 0.1.5 `load_rosters`, whose guard is `not isinstance(season, int) or season < 1920 or season > current_roster_year`. `isinstance(np.int64(2025), int)` is `False`, so the in-range season tripped the type clause. The broad `except Exception` in `_apply_expert_predictions` swallowed it, leaving stable-null columns. RotoWire was immune (sleeper's `_validate_sleeper_seasons` coerces via `{int(s) for s in seasons}`; `player_ids()` takes no season). Latent since the `nfl_data_py`→`nflreadpy` migration added the strict guard. Only the *cold* path hits it — a warm `nflcom_projections_joined_*` cache returns before the `rosters` call, which is why a dev box with the cache (and the unit fixtures) never reproduced it; the ECS container boots cold.
- **Fix:** Return native Python ints: `sorted(int(s) for s in seasons.astype(int).unique())`. Serving-only edit (no model fingerprint change, no retrain), so a fresh container would re-hydrate the stale null cache — bumped `_PREDICTIONS_CACHE_SCHEMA_VERSION` 5→6 so hydrate detects a schema mismatch and recomputes the corrected expert join. Verified on the true cold path (deleted the joined cache → real `rosters()` call → `nflcom_pred_ppr` populated 3/3 with default loaders). The serving PR did NOT touch `nfl_source.rosters`/`nflcom_loader.py` (a `src/data/` edit fires a 6-position retrain). **Follow-up:** added `_native_int_seasons` in [../src/data/nfl_source.py](../../src/data/nfl_source.py) — the single nflreadpy boundary now coerces every season-list wrapper (`rosters`/`rosters_weekly`/`weekly_data`/`schedules`/`snap_counts`/`injuries`/`depth_charts`/`pbp_data`/`ff_opportunity`) to native int, protecting all callers. Shipped `[docs-only]` because it is unconditionally model-inert (`int(s)` changes only the type, never the value, so fetched data and trained models are byte-identical), which skips the otherwise-wasteful retrain.
- **Lesson:** `numpy.int64` is **not** a Python `int` (`isinstance(np.int64(x), int) is False`), and nflreadpy 0.1.5's season loaders (`load_rosters`/`load_pbp`/`load_rosters_weekly`/`load_snap_counts`/`load_injuries`/`load_participation`/`load_ffverse`) all reject it with a range-worded message that hides the type cause. Any season list derived from a DataFrame (`.unique()`/`.astype(int)`) must be coerced to native int before crossing the nflreadpy boundary. A "metric/expert column all-null" bug whose loader is wrapped in `except Exception` is invisible without reading the served artifact + the container logs — `git`/unit tests can't see it (cache + fixtures mask the cold path). And a serving-only data-correctness fix needs a cache-version bump to take effect, because the prediction-cache fingerprint keys on model/data files, not serving code.
