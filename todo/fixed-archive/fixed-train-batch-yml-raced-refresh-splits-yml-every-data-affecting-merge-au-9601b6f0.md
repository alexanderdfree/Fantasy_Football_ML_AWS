### [FIXED] `train-batch.yml` raced `refresh-splits.yml` → every data-affecting merge auto-retrained one commit behind
- **File(s):** [.github/workflows/refresh-splits.yml](../../.github/workflows/refresh-splits.yml) (writes per-SHA `splits-rebuild-markers/{pending,ready}/${SHA}.txt` around the regen+upload), [.github/workflows/train-batch.yml](../../.github/workflows/train-batch.yml) (new "Wait for fresh data splits" gate before "Submit Batch jobs and wait").
- **What:** A merge touching splits-affecting paths (`src/data/**`, skill configs) fires BOTH `refresh-splits.yml` (rebuild `data/splits/` → S3, ~14 min) and the `batch-image.yml`→`train-batch.yml` chain (build image ~9 min, then download splits from S3 and train) — concurrently, from the same push. Because the image build (~9 min) is shorter than the splits rebuild (~14 min), train downloaded the **previous** commit's splits and trained one commit behind. Proven by the #383 `nflreadpy` migration: the auto-retrain (`d1043f1`) produced metrics **byte-identical** to the pre-migration baseline (`ff0d119`) — deterministic Ridge MAE identical across all 6 positions ⟺ identical (old) training data — while a manual break-glass dispatch run 6 min after refresh-splits finished (`b7b35ba`) trained on the new data (RB NN MAE −0.258, TE −0.147, all positions ≤0; K/DST flat). `refresh-splits.yml`'s own comment even noted "train-batch.yml fires independently."
- **Fix:** A **fail-safe** splits-freshness gate. refresh-splits writes a "pending" marker before the rebuild and a "ready" marker after the S3 upload, keyed by `github.sha` (= train-batch's `workflow_run.head_sha`, matching the `job-def-revisions/${SHA}.txt` convention). train-batch polls before submitting: ready present → proceed; no pending → refresh-splits didn't fire (no splits change) → proceed immediately; pending-but-not-ready → poll ~20 min for ready, then proceed (`::warning::`) on timeout. **Every path proceeds** — a gate bug degrades to the old behavior, never blocks the GPU pipeline.
- **Lesson:** Two workflows triggered by the same push and sharing an S3 artifact race unless one explicitly waits for the other. Put the producer/consumer handshake in an S3 marker keyed by `workflow_run.head_sha` (NOT `gh run list --commit`, which exposes a *different* run-level head_sha — see the `dedup_check` comment). The race was invisible to every prior merge (splits rarely change materially) and surfaced only on a data-source migration; it was diagnosed by comparing **deterministic Ridge** MAE across auto vs manual retrains — an NN-only comparison would've been masked by run-to-run variance.
- **Follow-up (2026-05-29):** PR #516 gated only `train-batch.yml`. [train-ec2.yml](../../.github/workflows/train-ec2.yml) (the `BATCH_ACTIVE=false` warm-EC2 rollback path) shares the same `batch-image.yml`→`workflow_run` trigger and downloads `data/splits/` from S3 inside `ff-train`, so it had the **identical** race — latent while Batch is active, but exactly the path a rollback depends on. Extended the same fail-safe pending/ready gate to it, and added [tests/test_train_split_gate.py](../../tests/test_train_split_gate.py): a YAML-parse contract test pinning the wait gate on BOTH train workflows + the refresh-splits pending/ready marker writes (PR #516 shipped the gate untested, so this guards against a silent regression of either half of the handshake). **Lesson:** when a fix lands on the active path, grep for sibling consumers of the same trigger/artifact — the rollback path is easy to miss precisely because it's inactive.
