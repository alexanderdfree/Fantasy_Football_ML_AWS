# ADR-0016: External opportunity / quality / value signals (ff_opportunity, ESPN QBR, contracts)

**Status:** Accepted

**Decision.** Three external nflverse sources feed the models through the D6 allowlist and the D4 history/static split: **ff_opportunity** expected-points stats (per-game → attention history for QB/RB/WR/TE; prior-season mean → static), **ESPN QBR** (per-game → QB attention history; prior-season mean → QB static), and **player contracts** (static only, all individual-player positions). A new [src/data/external_sources.py](../../src/data/external_sources.py) module owns the fetch + transform; [src/data/loader.py](../../src/data/loader.py)::`load_raw_data` merges the results onto the weekly frame alongside the existing snap/injury/depth/red-zone merges.

**Context.** The models learned opportunity, efficiency, and player-value only indirectly (rolling volume, snap %, depth-chart rank). ff_opportunity's *expected* stats are a cleaner usage/role signal than raw volume; QBR is an opponent-adjusted QB-quality signal orthogonal to the box score; contract APY-as-a-share-of-cap is a slowly-changing "team investment / expected role" prior. All three are standard nflverse/ffverse data the pipeline already had the plumbing pattern for.

**Chosen split (per D4/D6).** Per-game values → `ATTN_HISTORY_STATS` (leakage-safe via `build_game_history_arrays`, which uses prior in-season games only — the same mechanism that makes the player's own `passing_yards` safe there). Player-level aggregates → the static branch as **prior-season means** (`prior_season_mean_*`), the static-legal shape under D6; career-cumulative is deliberately *excluded* from static, matching the `career_carries`-forbidden-from-static precedent locked by `tests/test_attn_static_columns.py`. Expected fantasy points are used as a **feature, never a target** — D6's raw-stat-target rule is untouched (component `*_exp` preferred over the `total_*_exp` aggregate where it maps to a predicted stat). Contracts are collapsed to the contract *in effect as of each season* via `pd.merge_asof` on `year_signed`; `apy_cap_pct` is the cross-era-normalized headline.

**Fetch / ID notes.** All fetches route through the `nfl_source` shim (the nflreadpy boundary from the 2026-05-29 migration above), so `external_sources.py` imports no data library directly. `nfl_source.ff_opportunity` / `nfl_source.contracts` wrap nflreadpy's `load_ff_opportunity` / `load_contracts`; nflreadpy has **no** QBR loader, so `nfl_source.qbr_weekly` reads the nflverse espnscrapeR-data CSV directly (the same source the retired `nfl_data_py.import_qbr` used). ff_opportunity + contracts are gsis-keyed (join directly); QBR is ESPN-id-keyed, bridged to gsis via `nfl_source.player_ids()` (`load_ff_playerids` — the crosswalk the snap-count merge shares). ff_opportunity ships `season` as str / `week` as float, so a `_coerce_merge_keys` step normalises `(player_id, season, week)` to weekly's dtypes before the merge. Each source caches a season-keyed parquet mirroring the loader convention, and every merge dedupes on its join keys so it can't fan out player-week rows.

**Rejected.** (a) *New `include_features` categories* (`opportunity`/`qbr`/`contract`) — `flatten_include_features` hard-validates category names against a fixed `INCLUDE_CATEGORY_ORDER`, so the new static features were folded into the existing `prior_season` (aggregates) and `contextual` (contracts) categories instead, which also keeps them in the D6 attention-static allowlist with no machinery change. (b) *Rolling/windowed versions of the per-game signals for Ridge/LightGBM* — out of scope this pass (NN-history-only); the static prior aggregates still reach all three models via `include_features`. (c) *Career-cumulative static aggregates* — kept in the history domain per the D6 static-branch convention.

**Consequence.** New raw columns must be present in `data/splits/*.parquet`, so a splits regen (refresh-splits path) + S3 refresh is required before training/serving pick them up; until then `build_game_history_arrays` fails loud (by design). Serving needs no code change — it reuses `build_position_features` + the saved attn config lists, so the new history/static features flow through automatically once the splits carry the raw columns.
