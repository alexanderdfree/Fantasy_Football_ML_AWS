# ADR-0017: Platform autodetection & per-arch optimization policy

**Status:** Accepted

**Decision.** Platform-specific behaviour is chosen by **autodetection with an environment-variable override**, and the canonical "what hardware is this?" report lives in one module — [src/shared/platform_detect.py](../../src/shared/platform_detect.py)::`detect_platform`. The project trains/tunes/benchmarks/tests across six environments — Apple Silicon macOS, Windows 11 / WSL2 on an RTX 5080 (Blackwell `sm_120`), and AWS g4dn.xlarge (T4, `sm_75`) / g6.xlarge (L4, `sm_89`) — and any per-platform optimization branches off `detect_platform()` rather than sniffing `platform.system()` / `torch.cuda.is_available()` ad-hoc. The **training metric path is held constant across all of them** (static FP16 AMP on CUDA, FP32 off-CUDA, per D12); per-arch divergence is confined to speed knobs that don't change numerics and to opt-in flagged paths.

**Context.** The same models run on machines with very different accelerators (none / MPS / T4 / L4 / Blackwell), CUDA capabilities (no native BF16 on the T4; BF16 on `sm_80+`), CPU counts (4 vCPU on AWS vs 16 cores on the 9950X3D), and OSes (the native-Windows OpenBLAS `0xC0000005` crash that WSL2 / Linux / macOS don't hit). Device/dtype/thread handling already existed but piecemeal and undocumented as a policy. Without a stated rule, a "make it fast on the box I'm on" change risks either breaking another target or silently making cross-machine benchmark numbers incomparable.

**Chosen.** (a) `detect_platform()` reports `backend` / `gpu_name` / `compute_capability` / `sm` / `supports_bf16` / `os` / `is_wsl` / `cpu_count` / `recommended_cuda_wheel` and is reporting-only. (b) Device resolution stays in [src/shared/utils.py](../../src/shared/utils.py) (`requested_device` / `cuda_enabled` / `mps_enabled`): the operator's `FF_DEVICE` (`auto` / `cpu` / `cuda` / `mps`, via `run_pipeline --device`) layered on detection; `auto` is CUDA-or-CPU and never MPS, keeping the default path byte-identical to CI. (c) MPS is wired as **opt-in** (`FF_DEVICE=mps`) — runnable for benchmarking on a Mac but never auto-selected. (d) Per-platform install uses the existing split wheels ([requirements-dev.txt](../../requirements-dev.txt) cpu / [requirements-gpu.txt](../../requirements-gpu.txt) cu128 / [src/batch/Dockerfile.train](../../src/batch/Dockerfile.train) cu126); CPU/BLAS knobs via `LGBM_N_JOBS` + the per-OS guidance in [SETUP.md](../../SETUP.md).

**Rejected.** (a) *Per-arch training-dtype default* (e.g. BF16 on the L4 / Blackwell now that the Batch CE is on g6) — FP16 stays the default on every CUDA GPU. BF16 is exposed as an opt-in (`FF_AMP_DTYPE=bf16`, sm_80+, #640) but stays non-default because it hung the T4 (PR [#293](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/293)/[#301](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/301)) and a deterministic 5080 A/B measured it *regressing* high-magnitude heads (#640); one default dtype also keeps cross-GPU benchmark numbers comparable. The sanctioned per-arch *speed* knobs — opt-in `torch.compile` (`FF_COMPILE`, sm_80+, #641) and auto TF32 — do not change the metric. Revisiting the dtype default needs a comparability argument, not "the GPU supports it" (extends [D12](0012-training-step-perf-composition.md)). (b) *MPS as the macOS auto-default* — no proven speedup for this small attention model, breaks CPU/CI byte-identity, and risks silent op-fallback; opt-in plus an A/B is the bar to flip it. (c) *Ad-hoc `platform.system()` sniffing* scattered through the pipeline — centralized in `detect_platform()` so the per-arch decision table lives in one place.

**Consequence.** New per-platform work has a single reuse point and a documented matrix (the *Platform & hardware targets* section of [CLAUDE.md](../../CLAUDE.md)). Because `src/shared/` is in the path-based retrain trigger, even a numerically-inert detection refactor fires a 6-position retrain — verify the no-op via the Ridge-identity tell, or mark the commit training-skipped.
