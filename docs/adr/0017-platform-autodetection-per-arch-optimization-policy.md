# ADR-0017: Platform autodetection & per-arch optimization policy

**Status:** Accepted

**Decision.** Platform-specific behaviour is chosen by **autodetection with an environment-variable override**, and the canonical "what hardware is this?" report lives in one module — [src/shared/platform_detect.py](../../src/shared/platform_detect.py)::`detect_platform`. The project trains/tunes/benchmarks/tests across seven environments — Apple Silicon macOS, Windows 11 / WSL2 on an RTX 5080 (Blackwell `sm_120`), and AWS g4dn.xlarge (T4, `sm_75`) / g5.xlarge (A10G, `sm_86`) / g6.xlarge (L4, `sm_89`) — and any per-platform optimization branches off `detect_platform()` rather than sniffing `platform.system()` / `torch.cuda.is_available()` ad-hoc. The **training metric path is held constant across all of them** (static FP16 AMP on CUDA, FP32 off-CUDA, per D12); per-arch divergence is confined to speed knobs that don't change numerics and to flagged paths — with one **deliberate exception (2026-06-05; see Changelog): `FF_CUDA_GRAPH` autodetects ON for sm_80+ and intentionally moves the metric path per-arch**, shipped with a graphed benchmark rebaseline rather than held byte-identical.

**Context.** The same models run on machines with very different accelerators (none / MPS / T4 / L4 / Blackwell), CUDA capabilities (no native BF16 on the T4; BF16 on `sm_80+`), CPU counts (4 vCPU on AWS vs 16 cores on the 9950X3D), and OSes (the native-Windows OpenBLAS `0xC0000005` crash that WSL2 / Linux / macOS don't hit). Device/dtype/thread handling already existed but piecemeal and undocumented as a policy. Without a stated rule, a "make it fast on the box I'm on" change risks either breaking another target or silently making cross-machine benchmark numbers incomparable.

**Chosen.** (a) `detect_platform()` reports `backend` / `gpu_name` / `compute_capability` / `sm` / `supports_bf16` / `os` / `is_wsl` / `cpu_count` / `recommended_cuda_wheel` and is reporting-only. (b) Device resolution stays in [src/shared/utils.py](../../src/shared/utils.py) (`requested_device` / `cuda_enabled` / `mps_enabled`): the operator's `FF_DEVICE` (`auto` / `cpu` / `cuda` / `mps`, via `run_pipeline --device`) layered on detection; `auto` is CUDA-or-CPU and never MPS, keeping the default path byte-identical to CI. (c) Apple MPS is wired as **opt-in** (`FF_DEVICE=mps`) — runnable for benchmarking on a Mac but never auto-selected. NVIDIA CUDA MPS is a separate Linux-only process-concurrency tool; it is allowed for offline AWS Batch tuning where g6/L4 or g5/A10G Linux can actually run `nvidia-cuda-mps-control`, and must remain an explicit tuner profile rather than a production training default. (d) Per-platform install uses the existing split wheels ([requirements-dev.txt](../../requirements-dev.txt) cpu / [requirements-gpu.txt](../../requirements-gpu.txt) cu128 / [src/batch/Dockerfile.train](../../src/batch/Dockerfile.train) cu126); CPU/BLAS knobs via `LGBM_N_JOBS` + the per-OS guidance in [SETUP.md](../../SETUP.md).

**Rejected.** (a) *Per-arch training-dtype default* (e.g. BF16 on the L4 / Blackwell now that the Batch CE is on g6) — FP16 stays the default on every CUDA GPU. BF16 is exposed as an opt-in (`FF_AMP_DTYPE=bf16`, sm_80+, #640) but stays non-default because it hung the T4 (PR [#293](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/293)/[#301](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/301)) and a deterministic 5080 A/B measured it *regressing* high-magnitude heads (#640); one default dtype also keeps cross-GPU benchmark numbers comparable. The sanctioned per-arch *speed* knobs — opt-in `torch.compile` (`FF_COMPILE`, sm_80+, #641) and auto TF32 — do not change the metric. Revisiting the dtype default needs a comparability argument, not "the GPU supports it" (extends [D12](0012-training-step-perf-composition.md)). (b) *MPS as the macOS auto-default* — no proven speedup for this small attention model, breaks CPU/CI byte-identity, and risks silent op-fallback; opt-in plus an A/B is the bar to flip it. (c) *Ad-hoc `platform.system()` sniffing* scattered through the pipeline — centralized in `detect_platform()` so the per-arch decision table lives in one place.

**Consequence.** New per-platform work has a single reuse point and a documented matrix (the *Platform & hardware targets* section of [AGENTS.md](../../AGENTS.md)). Because `src/shared/` is in the path-based retrain trigger, even a numerically-inert detection refactor fires a 6-position retrain — verify the no-op via the Ridge-identity tell, or mark the commit training-skipped.

**References.** [src/shared/platform_detect.py](../../src/shared/platform_detect.py), [src/shared/utils.py](../../src/shared/utils.py), [src/shared/pipeline.py](../../src/shared/pipeline.py) (`_nn_device`), [src/shared/training.py](../../src/shared/training.py) (`_autocast` AMP-dtype rationale), [tests/shared/test_platform_detect.py](../../tests/shared/test_platform_detect.py), [tests/shared/test_device_selection.py](../../tests/shared/test_device_selection.py), [AGENTS.md](../../AGENTS.md) (*Platform & hardware targets*), [SETUP.md](../../SETUP.md). - **2026-06-11** — **`FF_CUDA_GRAPH_FULL` opt-in full-step capture (tune-first).** [src/shared/training.py](../../src/shared/training.py) gains `_GraphedTrainStep` + `MultiHeadTrainer._maybe_graph_full_step`: one `make_graphed_callables` capture covering batch gather (`index_select` on the resident batcher tensors) + model forward + a branch-free `MultiTargetLoss.compute_combined_capturable` (hurdle families swap `if pos_mask.any():` for the algebraically identical masked-sum form), leaving only the idx handoff + GradScaler/clip/optimizer tail eager per step. Gated by `cuda_graph_full_enabled()` ([src/shared/utils.py](../../src/shared/utils.py)) = `FF_CUDA_GRAPH_FULL` truthy AND the base sm_80+ gate — **opt-in, default OFF for training** (the owner approved one graphed rebaseline; a second silent capture-scope change would re-open benchmark comparability). - **2026-06-07** — **GPU-resident dataloaders now gate on the trainer's device too (residency is opt-in).** Follow-up to the CUDA-graph device-gate below — the same root cause in a second helper. `_gpu_resident_device` ([src/shared/training.py](../../src/shared/training.py)) and the four `make_*_dataloaders` factories chose the `_GPUResidentBatcher` from the *global* `cuda_enabled()`, so a `device=cpu` trainer on a GPU box (the per-position `@integration` regression tests) got GPU-resident, differently-shuffled loaders → the tiny-data NN converged to wildly different minima (MAE 60–100 vs LGBM 5–15), flaky run-to-run; green on CPU/CI, graph-independent. Made residency **opt-in by the caller's device**: `_gpu_resident_device(device)` returns the resident device only when `device` is CUDA, the factories take `device=None` (default → plain `DataLoader`), and [src/shared/pipeline.py](../../src/shared/pipeline.py) passes the resolved `_nn_device()` at all five call sites. **Numerically inert on production** — a GPU host resolves `_nn_device()` to cuda, so residency engages with the same device as before (e2e pipeline tests pass on GPU); tests / CPU callers default to the deterministic DataLoader (CI-faithful local runs). Zero per-test edits — only the 5 production call sites + the factory signatures changed. Verified: all-position regression+training 131 passed ×2 under `-n 8` (was 6 failed), `pytest -m unit` 2536 passed on the 5080.
- **2026-06-07** — **CUDA-graph capture now gates on the trainer's own device, not just the global capability.** `MultiHeadTrainer._maybe_graph_model` ([src/shared/training.py](../../src/shared/training.py)) previously returned early only on `not cuda_graph_enabled()` — a *host* capability check (autodetect-ON for any sm_80+ box). - **2026-05-31** — Local parallel trainer ([src/benchmarking/parallel_train.py](../../src/benchmarking/parallel_train.py)) gains a **work-conserving CPU core pool** ([src/shared/core_pool.py](../../src/shared/core_pool.py)) — a speed-only, numerically-inert instance of this policy for the many-core WSL2 / 9950X3D target. An `AF_UNIX` coordinator owns the box's physical cores; each position leases its fair share (`ceil(total / active)`) per CPU stage (Ridge/ENet CV, LightGBM) via `lease_cores`, releasing on stage exit, so cores freed by a finished position widen the survivors' *thread counts* — not just their affinity, which the prior static per-slice `LGBM_N_JOBS` could never do (it was immutable post-spawn, so freed cores were stranded). Opt-in via `FF_CORE_POOL_ADDR` (set only by the orchestrator); unset = a byte-identical no-op for `run_pipeline` / AWS Batch / pytest. `n_jobs` threads through `_tune_ridge_alphas_cv` / `_tune_enet_cv` / `LightGBMMultiTarget` (thread count only — MAE unchanged, the Ridge-identity tell). Dispatch order is derived from measured `benchmark_history` `elapsed_sec` (static `_COST_ORDER` fallback).
