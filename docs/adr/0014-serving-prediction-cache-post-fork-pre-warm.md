# ADR-0014: Serving prediction cache and post-fork pre-warm

**Status:** Accepted

**Decision.** Cache the assembled historical predictions, metrics, source fingerprint and browser snapshot as one immutable generation. Store generations under `data/serving_cache/generations/{content-id}/` and atomically replace `current.json` only after every member and its checksum manifest is complete. A reader resolves the pointer once and keeps that directory for its whole read. Individual files in a published generation are never rewritten or removed by another worker.

**S3 publication.** `src/shared/prediction_cache.py` packages one generation into `models/predictions_cache/cache.tar.gz`; `model_sync.py` uploads it with one PUT and downloads/verifies the entire object before switching the local pointer. The new object is isolated from old containers' loose-file uploads. Legacy loose triples cannot establish a common generation and are deliberately not a hydration fallback. Failed/partial transfers preserve the previous complete generation. Local old generations remain on the ephemeral task filesystem until task replacement, protecting readers that already resolved an older pointer.

**Validity.** Hydration requires the current serialization schema and model/data fingerprint and verifies every cache member's checksum. The fingerprint is captured before inference, after base data preparation, and checked again before publication; a refresh during inference or serialization cannot label old predictions with new inputs. Hydration also rechecks inputs after decoding. The optional snapshot is serialized from the same locked results and committed with the required cache members. A missing snapshot may be regenerated from the exact generation just hydrated.

**Runtime.** Each gunicorn worker retains its own in-memory cache. `post_fork` starts a daemon pre-warm thread after the master binds; lazy requests share the same reentrant cache lock. Pre-warm at module import under `--preload` remains prohibited: it prevents the listener binding and caused the #148/#149 health-check failures. Cold cache computation remains a fallback; this decision does not move heavy upcoming-week feature building into serving. Upcoming projections retain the separate CI-built artifact contract in ADR-0018.

**Deployment and migration.** Deploy prepares a matching generation in CI before replacing ECS tasks. The cache builder's `--reuse-valid` mode syncs current inputs and the bundle, reuses a complete valid generation, and otherwise builds and publishes through the existing off-container path. Preparation failure blocks the deploy. This seeds the new bundle protocol before its first serving rollout and avoids forcing every new worker into cache-miss inference. The regular split-refresh builder still forces a rebuild. Future model changes after this preparation can still cause a runtime miss; the broader post-train cache-build work remains tracked by issue #1140.

**In-flight refresh.** A master poller watches the per-position model manifests; a successfully installed model advances its on-disk sentinel. Aggregate checks inspect both loaded and failed positions' recorded sentinels. An advanced sentinel invalidates the worker's aggregate and reloads the affected positions. Unchanged failures do not cause retry storms. Sentinel-triggered computation must not rehydrate the generation it invalidated, including when model fingerprint bytes happen to be unchanged. A worker records that generation's ID locally; it never unlinks another worker's generation or its newly published pointer. K/DST retain their authoritative split/history refresh paths.

**Health.** Unattempted cold start returns HTTP 200. An affirmative shared base-data initialization failure, or errors with no usable loaded positions, returns 503. Useful partial-position failure stays 200 with degraded status. Successful base initialization or cache hydration clears the shared failure marker. Public health responses retain position keys but sanitize exception details; full diagnostics remain in logs.

**Browser API.** `/api/snapshot` resolves the committed generation and verifies schema, input fingerprint and checksums without invoking model loading or inference. It returns 404 when no eligible snapshot exists, allowing the existing live-API fallback. `Cache-Control: no-cache` keeps browser revalidation. The snapshot payload remains `{generated_at, weeks, degraded_positions, scoring}`; no frontend contract change is required.

**Tradeoffs.** Compared with independent per-file writes, the bundle adds temporary serialization buffers and checksum I/O, while removing cross-worker and cross-task mixed-generation reads. Generation files use task-local disk until replacement. S3's one-object atomicity does not require a new coordination service. Cache schema and input fingerprint remain separate from the artifact publication order defined in ADR-0011.
