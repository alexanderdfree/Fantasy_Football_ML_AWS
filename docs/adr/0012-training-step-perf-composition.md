# ADR-0012: Training-step perf composition (torch.compile rejected on T4)

**Status:** Accepted

**Decision.** Apply four cheap, orthogonal training-step optimizations on the EC2 training host — Feather-cached parquet reads, `DataLoader(num_workers=2, pin_memory=True)` on CUDA, `torch.backends.cudnn.benchmark = True`, and `optimizer.zero_grad(set_to_none=True)` — and emit phase-level timings as part of every benchmark JSON. *Do not* enable `torch.compile`: on T4 with this workload it costs +32% wall time and the wrapper is short-circuited at the call site.

**Context.** A 2-minute training job × 6 positions × every commit to `main` puts wall-clock training time directly on the critical path between `git push` and serving (D7/D9). The four cheap optimizations are uncontroversial — they target distinct bottlenecks (disk parse, host→device copy, conv-kernel search, gradient-zero traffic) and compose linearly. `torch.compile` was the obvious "free win" candidate but the actual measurement on the EC2 g4dn (PR #189, `3167b56`) showed a consistent regression, and a parallel test of `LGBM_N_JOBS=-1` (PR #188) was unwittingly bundled with the compile regression in the same image, masking its signal entirely until both were unwound (PR #196).

**Options considered.** Multiple perf knobs evaluated against the same EC2 g4dn baseline:

| Knob | Wall-time delta | Why |
|---|---|---|
| Feather-cached parquet + async DataLoader + cuDNN benchmark + `set_to_none=True` (chosen, PR #183) | **−40% to −60%** depending on position | Disk parse amortized across positions; H→D copy overlapped with forward pass; cuDNN picks the best conv kernel per attention shape after warmup; no zero-write traffic on the gradient buffer |
| Static-pad attention sequences — hold `build_game_history_arrays`'s fixed `[n, 17, game_dim]` tensors instead of stripping to variable-length lists for a custom collate (chosen, PR #200) | **−30%** on attention training (115.8 s → 81.2 s on RB) | Default PyTorch collate stacks fixed-shape tensors with zero overhead; masked positions contribute zero regardless, so math is equivalent. K's nested-attention path already used this pattern; PR #200 brought QB/RB/WR/TE/DST in line |
| Disk-backed feature-engineering cache (`.cache/features/`, content-hashed) (chosen, PR #200) | **86×** on prepare_data for cache hits (8.6 s → 0.1 s on RB) | `_prepare_position_data` is deterministic given `(position, train_df, val_df, test_df, cfg)` but is called N_folds × N_trials × N_positions times during Optuna and across CLI re-runs. Bypass with `FF_FEATURE_CACHE_DISABLE=1`; metrics bit-identical across runs |
| CPU/GPU branch overlap inside `run_pipeline()` via `ThreadPoolExecutor` (chosen) | `cpu + gpu` → `max(cpu, gpu)` per position | Ridge/ElasticNet/LightGBM (CPU; BLAS, sklearn, LightGBM C++) and base NN/Attention NN (GPU; CUDA) had no inter-model data dependency until the post-train `comparison` block. Nested closures `_cpu_branch` + `_gpu_branch` capture the existing phases and dispatch concurrently with a 1-worker pool. Threading (not processes) reuses the GIL-releasing properties of BLAS/CUDA already exploited by the inner `joblib.Parallel(prefer="threads")` CV grids. New `train_models_total` phase timing exposes the win |
| `torch.compile(model, dynamic=True)` on every NN forward | **+32%** | T4 (sm_75) has too few SMs to amortize the fused-kernel benefit at this batch size; variable-length history sequences cause Inductor to re-check guards each batch, drowning the gain |
| LightGBM `n_jobs=-1` baked into the training image (PR #188) | "test confounded by `torch.compile`" | Reverted in PR #196 — never genuinely measured because the compile regression masked the signal. Needs a clean re-test now that `torch.compile` is off |

**Chosen rationale.** Keep the four cheap wins; short-circuit `_maybe_compile` in [src/shared/pipeline.py:150-176](../../src/shared/pipeline.py) so the path is dead code but the wrapper survives for a future hardware change (the docstring records the measurement and the conditions for re-enabling). LGBM threading is left as an open question — the default `LGBM_N_JOBS=1` is conservative but not currently regressed.

**Rejected.** `torch.compile` on T4 for variable-length sequences — re-evaluate if/when the training host moves to `sm_86+` (A10 or larger, more SMs). As of 2026-05-31 `_maybe_compile` exposes an **opt-in** re-enable gated to `FF_COMPILE=1` **and** sm_80+ (so T4 production stays the no-op path); it is off by default and must be benchmarked before trusting — the +32% was a T4 result, but the dynamic-shape guard-recheck caveat is hardware-independent. Bundling parallel perf experiments into one image — every "perf win" must be measured independently so a co-resident regression doesn't mask the signal (this is the lesson from PRs #188/#189/#196).

**Consequence.** Phase timings (`pipeline.nn_train`, `pipeline.attn_nn_train`, `pipeline.prepare_data`, `pipeline.ridge_tune`, etc.) are now part of every benchmark JSON ([benchmark_history/](../../benchmark_history/)), making perf regressions visible position-by-position without an explicit perf-test job. This composes with the per-shard `detect` logic in [.github/workflows/train-ec2.yml](../../.github/workflows/train-ec2.yml) so an unrelated regression on a non-changed position is still visible in the next run that touches it. The Feather cache adds one disk file per parquet under [src/batch/train.py](../../src/batch/train.py)'s cache path — must be regenerated when a feature schema changes (the cache is invalidated by mtime, so re-running training after a parquet rewrite picks up the change automatically).

**References.** [src/batch/train.py:87-132](../../src/batch/train.py) (Feather cache with mtime invalidation), [src/shared/pipeline.py:143](../../src/shared/pipeline.py) (`cudnn.benchmark` toggle), [src/shared/pipeline.py:150-176](../../src/shared/pipeline.py) (`_maybe_compile` short-circuit + restore instructions), [src/shared/training.py](../../src/shared/training.py) (`num_workers=_NUM_WORKERS, pin_memory=True` across all eight `DataLoader` sites: L448-461 / L509-522 / L948-961 / L1119-1132), [src/shared/training.py:650](../../src/shared/training.py) (`zero_grad(set_to_none=True)`), [src/shared/feature_cache.py](../../src/shared/feature_cache.py) (disk-backed feature-engineering cache with content-hashed keys; `FF_FEATURE_CACHE_DISABLE=1` bypass), [src/shared/models.py:30](../../src/shared/models.py) (`_LGBM_N_JOBS` env-var-only opt-in, default `1`). ## Changelog

- **2026-05-31** — D12 perf: launch-bound NN-loop hot-path cuts + the `torch.compile` measurement that resolves the #641 re-eval (#655). The NN training is **host-bound** (~20% GPU util on this small model), so per-step *host* overhead — not GPU FLOPs — sets wall-clock. Three cuts in [src/shared/training.py](../../src/shared/training.py) + [src/shared/pipeline.py](../../src/shared/pipeline.py): read `GradScaler.get_scale()` (a CPU-GPU sync) **only on the per-batch-scheduler path** (the default `cosine_warm_restarts` was paying 2 discarded syncs/batch); `AdamW(fused=True)` on CUDA (one fused kernel vs `foreach`'s several launches); hoist the per-batch entropy `getattr` above the loop + in-place loss accumulator. Measured **−15.6%** total wall-clock on QB (5080: `nn_train` −26%, `attn_nn_train` −5.8%), per-target MAE within ±2%. A deterministic `fused=True`-vs-`fused=False` isolation (QB, everything else fixed, **zero** within-side variance) pinned **fused AdamW as the only numerics-active change** (the `get_scale`/hoist cuts are inert): its true cost is **+0.89% `nn_mae` (base NN) and −0.18% `attn_nn_mae`** — i.e. the deployed attention model is *marginally better*, not worse. The +1.40% `nn_mae` seen in the first (non-deterministic, 2-run) A/B was variance-inflated; the isolated figure is ~0.9%. Comfortably inside ±2%, and the base NN isn't the production model for QB anyway. **Resolves D12's open `torch.compile` question** (the #641 `FF_COMPILE` opt-in / "retest on sm_86+"): a 5080 (sm_120) A/B measured `torch.compile(model, dynamic=True)` at **+169%** on `attn_nn_train` / +62% total — the dynamic-shape guard-recheck caveat is **hardware-independent**, so compile stays off on Blackwell/Ada (incl. the new L4 Batch host), not just the T4. Tests: [tests/shared/test_trainer_scheduler_perbatch.py](../../tests/shared/test_trainer_scheduler_perbatch.py). Relates to **D12**.
- **2026-05-31** — D12: `torch.compile` **opt-in re-enable**, gated to sm_80+. `_maybe_compile` ([src/shared/pipeline.py](../../src/shared/pipeline.py)) was a hard no-op after the +32%-on-T4 measurement; it now returns `torch.compile(model, dynamic=True)` **only when `FF_COMPILE` is truthy AND `torch.cuda.get_device_capability()[0] >= 8`** (Ampere/Ada/Blackwell — the T4's sm_75 stays the no-op path). Off by default, so CPU/Mac/CI and the T4 EC2 rollback are byte-identical to today. **Now directly relevant to the g6/L4 migration entry below**: L4 is sm_89 (≥ 8), so this is the mechanism to test that entry's "`torch.compile` re-eligible" follow-up on the actual production host — and a local experiment on the RTX 5080 (sm_120, many more SMs than the T4). The +32% regression was T4-specific, but the dynamic-shape guard-recheck caveat is hardware-independent — benchmark with vs without `FF_COMPILE=1` before trusting. Tests: [tests/shared/test_maybe_compile.py](../../tests/shared/test_maybe_compile.py). Relates to **D12**; stacks on the AMP-precision entry below.
- **2026-05-31** — D12: AMP-precision **`FF_AMP_DTYPE` opt-in + TF32** (FP16 stays the default everywhere; BF16 measured and rejected as a default). The NN autocast dtype now routes through `amp_dtype()` ([src/shared/utils.py](../../src/shared/utils.py)). **FP16 + GradScaler remains the default on every CUDA device** — T4 (sm_75), the **new L4/g6 Spot host (sm_89, see entry above)**, and Blackwell (RTX 5080 sm_120) alike: a deterministic RTX 5080 A/B (QB/DST, FP16 vs BF16) showed **BF16 regresses high-magnitude heads** — QB `passing_yards` +2.21% (attention NN) / +3.06% (base NN), headline `attn_nn_mae` +2.20% — because BF16 trades mantissa bits (7 vs FP16's 10) the model uses for exponent range it doesn't need (GradScaler already covers FP16 underflow), and FP16 runs full-throughput Tensor Cores on Ada/Blackwell anyway. The mantissa mechanism is architecture-independent, so this is **direct evidence against the L4-migration entry's "enable BF16" follow-up** — re-measure on L4 before flipping it. BF16 is **opt-in only** via `FF_AMP_DTYPE=bf16`, and *still* sm_80+-gated (it degrades to FP16 on T4 so the opt-in can't reintroduce the #293/#301 T4 hang); `fp32` disables AMP. CPU/MPS stay AMP-off → byte-identical to FP32. Also enables **TF32** for FP32 matmuls via `torch.set_float32_matmul_precision("high")` in `_nn_device` — kept because it's a hardware no-op on Turing (T4) and CPU/MPS yet accelerates the FP32 path on Ada/Blackwell (e.g. under `FF_AMP_DTYPE=fp32`); skipped under deterministic mode. The 5080 A/B confirmed TF32 has no measurable effect on the AMP path (det == non-det numbers). Net: **zero production-numerics change** (default is FP16, = prior behaviour); this adds an experimentation knob + the Ada/Blackwell FP32 speedup. Tests: [tests/shared/test_device_selection.py](../../tests/shared/test_device_selection.py). Relates to **D12** and the g6/L4 migration entry above; companion env-profile work in [scripts/wsl-env.sh](../../scripts/wsl-env.sh) + SETUP.md's WSL section.
- **2026-05-21** — D12 hardened (RNG correctness in CPU/GPU overlap path): one-line fix in [src/shared/training.py](../../src/shared/training.py)'s `_GPUResidentBatcher.__iter__` — `torch.randperm(self._n, device=self._device)` → `torch.randperm(self._n).to(self._device)`. PR [#309](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/309) (`04ef622`) introduced the GPU-resident batcher to replace the CUDA-side `DataLoader` (eliminating per-batch IPC + H2D copy), but its `__iter__` generated permutations on the CUDA device — silently switching from `torch.default_generator` (CPU) to `torch.cuda.default_generators[i]` (CUDA), which are independent streams that produce different sequences at the same numeric seed. The bug was universal across all 6 positions but visible primarily as a QB attn_nn aggregate MAE regression of +2.68% in the PR #307 production-validation run (driven by `passing_yards` head +4.50%, 68.35→71.43 yds — that head's Huber-δ=15 / ~250 yds/game magnitude amplifies batch-order drift the most). DST attn_nn improved -3.42% on the same code path — same drift, different loss-surface luck. CPU/MPS paths (which never enter `_GPUResidentBatcher`) are byte-identical to today; all 18 `tests/test_reproducibility.py` cases passed locally. The fix doesn't necessarily fully recover the 00c6d10 FP32 baseline because PR [#301](https://github.com/alexanderdfree/Fantasy_Football_ML_AWS/pull/301)'s FP16 autocast is a *separate* numerical-drift source for QB that's deferred (per-position `nn_use_amp=False` follow-up if QB still regresses >2% after this merge). Companion archive entry in [TODO.md](../../TODO.md) captures the "per-device default generators" structural lesson and the missing cross-path determinism test on PR #309's CI gate.
- **2026-05-20** — D12 extended: per-position `run_pipeline()` now overlaps its CPU branch (Ridge tune+fit, ElasticNet tune+fit, LightGBM) with its GPU branch (base NN + Attention NN) via a 1-worker `ThreadPoolExecutor` in [src/shared/pipeline.py](../../src/shared/pipeline.py). The two branches share read-only `X_train`/`y_train_dict`/`pos_*` and produce independent prediction dicts; the first place they meet is the `comparison` block, so the original sequential flow had no correctness reason to serialize. Wall-clock collapses from `cpu + gpu` to `max(cpu, gpu)` per position. Threading (not processes) because the CPU branch already nests `joblib.Parallel(prefer="threads")` for CV alpha grids and the GPU branch's PyTorch + CUDA both release the GIL — no pickling or process-spawn overhead. New `train_models_total` phase recorded in `phase_seconds` makes the overlap win visible alongside the existing per-phase timings.
