# ADR-0018: Live upcoming-week predictions homepage (ESPN-sourced)

**Status:** Accepted

**Decision.** The serving site gets a forward-looking **homepage** (the new default tab) showing model projections for the **next unplayed NFL week**, auto-refreshed in the background. The week's *live* inputs — schedule, Vegas lines, active rosters, injuries — come from **ESPN's free public API** ([src/serving/espn_live.py](../../src/serving/espn_live.py)); historical context (≤ latest played season, feeding `prior_season_*`) stays on nflverse. Synthetic player-week rows for the upcoming slate are spliced onto full nflverse history and run through the **real offline feature pipeline** (`load_raw_data` → `preprocess` → `engineer.build_features`), then the existing serving inference (`core._apply_position_models`) — so the upcoming week uses the training feature functions and encodings. A **scheduled CI job** ([src/serving/upcoming_week.py](../../src/serving/upcoming_week.py) `main`) builds the artifact and uploads it to S3; the serving container only **downloads + serves** it off disk (`sync_artifact_from_s3`); `GET /api/upcoming_week` serves it. **Scope: QB/RB/WR/TE/K/DST**. K/DST reuse their dedicated data and feature builders, with independent current-season inputs and explicit kick/opponent history injection.

**Context.** The site only showed backward-looking 2025 predictions; the actual fantasy use case is "who do I start next week." nflverse schedules carry only the *closing* line post-hoc and its roster/injury feeds lag, so a live source is required for the volatile inputs — but nflverse remains the only viable source for 10+ years of history. The cardinal risk is feature drift between a bespoke upcoming-week feature build and training; reusing `build_features` verbatim (the [D6](0006-explicit-per-position-feature-allowlist.md) anti-drift rule, mirrored from the [cross-player-feature parity](0016-external-opportunity-quality-value-signals.md) precedent) eliminates it.

**Chosen design.** (1) **ESPN client** isolates undocumented endpoints behind fixture-tested pure parsers; player identity bridges ESPN `athlete.id` → `espn_id` → `gsis_id` via the stable `nfl_source.player_ids()` crosswalk; the spread sign is flipped to nflverse's home-favored-positive convention. (2) **Frame builder** memoizes the historical `build_features` input (stable across polls) and concats synthetic rows (raw stats absent → features come from prior games via shift/rolling, so Week-1 cold-starts exactly as every trained Week-1 row does). (3) **Schedule-cache augmentation** splices the upcoming season's games into the on-disk `schedules_*.parquet` + resets `weather_features._schedule_cache` so `implied_team_total` (the top Week-1 feature) computes — all from `upcoming_week.py`, no `src/shared` edit, so no retrain. (4) **Current-week contextual enrichment**: the synthetic rows lack the externally-merged per-player columns (`depth_chart_rank`, contracts, injury/practice status); left NaN they fill to a constant and the QB attention head can't separate starters from backups and ~doubles every projection (verified 2026 W1: QB mean 30.7→9.6 after carrying `depth_chart_rank`/contracts forward + defaulting health columns). (5) **Out-of-serving build** — the heavy `load_raw_data` + `build_features` + inference runs in a scheduled CI job ([.github/workflows/refresh-upcoming-week.yml](../../.github/workflows/refresh-upcoming-week.yml): cron every 3h for fresh lines/injuries + on `train-batch` completion for new models + manual dispatch) and uploads the artifact to S3; the serving container `sync_artifact_from_s3` at boot + a lightweight S3-download poller (`FF_UPCOMING_SYNC_INTERVAL_S`, default 10 min), serving `503 warming` until the first build lands.

**Rejected.** (a) *nflverse for the live slate* — it lags; the user requirement is a direct live API. (b) *A separate odds-only API + nflverse for the rest* — only solves the single most-volatile input and still rides the nflverse cadence for rosters/injuries. (c) *In-serving background poller* — tried first (simpler, fresher), but **abandoned after two failed deploys**: running `load_raw_data`/`build_features` in the 2-worker serving task OOM-killed a worker and attempted a runtime 2025-PBP download that failed (SSL), so the new tasks never passed ELB `/health` and the circuit breaker rolled back — at both 2 *and* 4 vCPU. The scheduled-CI build (now chosen, (5) above) keeps that heavy/network work out of serving entirely. (d) *Recomputing only the new rows* — `build_features`' cross-player/season groupbys need the full frame; deferred as a perf optimization.

**Consequence.** The original skill-position rollout was serving-only. The K/DST extension adds optional input injection to their data loaders without changing the default training recipe; those loader paths still trigger the standard K/DST validation and retrain scoping. **Build location (learned the hard way):** two in-serving deploys rolled back — first a worker OOM-kill, then a runtime 2025-PBP download failure — **even at 4 vCPU / 8GB** — because a 2-worker serving task simply can't host the full `load_raw_data` + `build_features` + inference (PBP rebuild + GitHub PBP downloads). So the build moved to a scheduled CI job (ample memory + reliable network) that uploads the artifact to S3; serving downloads + serves it and is back to **2 vCPU / 4GB** (`infra/aws/task-definition.json` + live revision 454). `deploy.yml` also drops the 20-min in-workflow stability wait (`wait-for-service-stability: false`); the ECS circuit breaker still guards prod. ESPN endpoints are unofficial — a schema drift fails `espn_live.py`'s parsers loudly (fixture-tested), not the whole site, and the poller's broad try/except keeps serving up. K/DST controls follow the artifact\'s available positions, so old artifacts remain readable during rollout.

## K/DST source contract

The six-position CI refresh passes one verified `live_schedule` calendar and its per-game weather coverage into the K/DST builder, so venue, surface, odds, and forecast values agree across all positions. The standalone K/DST builder retains the gazetteer fallback described below when no enriched calendar is supplied.

The CI builder combines historical caches with freshly fetched current-season records. It admits only completed games before the forecast week, appends outcome-free target rows, and never changes `TRAIN_SEASONS`, `VAL_SEASONS`, or `TEST_SEASONS`. DST gets a placeholder QB row per target team so its existing shifted opponent aggregates are materialized for that week; these placeholders never enter the opposing-offense history input. Current kick and opponent histories are function arguments rather than mutations of the serving cache.

Weather uses the event's venue and UTC kickoff. A stadium gazetteer linked from [nflverse-data issue #57](https://github.com/nflverse/nflverse-data/issues/57), plus explicit newer international venues, resolves coordinates. Unknown venue mappings produce unavailable weather instead of a home-city guess. ESPN's outdoor flag overrides inherited venue defaults (the 2026 Melbourne game was labeled a dome in the schedule); an indoor flag alone does not establish a retractable roof's game-day state. [Open-Meteo](https://open-meteo.com/en/docs) forecasts use Fahrenheit and mph, enforce a bounded kickoff-hour match, and expose retrieval time and per-game availability. Historical replay supplies historical context explicitly; it does not fetch today's forecast for a past game.

Availability is separate from model improvement. This extension does not retune weights, change feature whitelists, or claim an accuracy gain. A new opponent-starter or opportunity feature remains a separate measured A/B decision.


## Freshness, availability and live metadata

Publication requires structurally valid scoreboards and one successful ESPN injury snapshot for the requested season, no more than four hours old, covering every scheduled team. A missing events list or incomplete game is a source failure, not a verified empty slate. Out exclusions, opportunity vacancies and numeric game status derive from that same injury response. Missing team rosters, malformed injury identities/statuses or an unavailable injury response stop publication; they do not imply healthy players. Every published position must contain usable model predictions. Verified offseason transitions are published to S3 too, replacing the previous active slate.

The read-only endpoint attaches a `freshness` object computed from the oldest of artifact generation, input retrieval and the injury source's own timestamp. Downloads never reset that age. Four hours is the stale threshold for the existing three-hour CI build cadence plus build/download headroom. Last-good predictions remain inspectable with a stale warning. The browser revalidates on mount, every five minutes, focus/visibility and manual Refresh; warming/errors retry after thirty seconds, retain last-good rows with warnings, and preserve the original generation time. This remains an off-container build; the endpoint does no feature building or source fetching.

Supplementary history sources report observed/expected completed player-game coverage and distinguish unavailable, partial, available and not-needed data. Missing snaps/opportunity statistics retain the existing trained encoding and are disclosed via `data_quality`, never represented as newly observed zeros. Live QBR can recover missing cells from the same upstream ESPN QBR API, using named Total QBR/points-added fields, completed game/season/week validation and player-team-game identity. Valid archived cells retain precedence. No proxy statistic, new feature, historical cache rewrite or training-recipe change is introduced.

Age/rookie metadata uses the fetched current-season weekly roster and actual game schedule. Season-matched ESPN roster DOB/debut/experience fields fill remaining display-only gaps; team-unit DST rows remain null. Historical metadata callers retain their cached source path. NFL.com community-archive projections are enabled by default only through the verified 2025 archive; operators may set `FF_UPCOMING_NFLCOM=1` after verifying current coverage. This is an availability policy, not a claim that the third-party archive is permanently discontinued. ESPN and RotoWire remain independently labeled live comparisons.
