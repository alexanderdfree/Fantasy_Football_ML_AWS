# ADR-0018: Live upcoming-week predictions homepage (ESPN-sourced)

**Status:** Accepted

**Decision.** The serving site gets a forward-looking **homepage** (the new default tab) showing model projections for the **next unplayed NFL week**, auto-refreshed in the background. The week's *live* inputs — schedule, Vegas lines, active rosters, injuries — come from **ESPN's free public API** ([src/serving/espn_live.py](../../src/serving/espn_live.py)); historical context (≤ latest played season, feeding `prior_season_*`) stays on nflverse. Synthetic player-week rows for the upcoming slate are spliced onto full nflverse history and run through the **real offline feature pipeline** (`load_raw_data` → `preprocess` → `engineer.build_features`), then the existing serving inference (`core._apply_position_models`) — so the upcoming week is featurized byte-identically to training. A background poller writes a serve-off-disk JSON artifact ([src/serving/upcoming_week.py](../../src/serving/upcoming_week.py)); `GET /api/upcoming_week` serves it. **Scope: QB/RB/WR/TE**; K/DST (separate, season-bound pipelines) are a follow-up.

**Context.** The site only showed backward-looking 2025 predictions; the actual fantasy use case is "who do I start next week." nflverse schedules carry only the *closing* line post-hoc and its roster/injury feeds lag, so a live source is required for the volatile inputs — but nflverse remains the only viable source for 10+ years of history. The cardinal risk is feature drift between a bespoke upcoming-week feature build and training; reusing `build_features` verbatim (the [D6](0006-explicit-per-position-feature-allowlist.md) anti-drift rule, mirrored from the [cross-player-feature parity](0016-external-opportunity-quality-value-signals.md) precedent) eliminates it.

**Chosen design.** (1) **ESPN client** isolates undocumented endpoints behind fixture-tested pure parsers; player identity bridges ESPN `athlete.id` → `espn_id` → `gsis_id` via the stable `nfl_source.player_ids()` crosswalk; the spread sign is flipped to nflverse's home-favored-positive convention. (2) **Frame builder** memoizes the historical `build_features` input (stable across polls) and concats synthetic rows (raw stats absent → features come from prior games via shift/rolling, so Week-1 cold-starts exactly as every trained Week-1 row does). (3) **Schedule-cache augmentation** splices the upcoming season's games into the on-disk `schedules_*.parquet` + resets `weather_features._schedule_cache` so `implied_team_total` (the top Week-1 feature) computes — all from `upcoming_week.py`, no `src/shared` edit, so no retrain. (4) **Current-week contextual carry-forward**: the synthetic rows lack the externally-merged per-player columns (`depth_chart_rank`, contracts, injury/practice status); left NaN they fill to a constant and the QB attention head can't separate starters from backups and ~doubles every projection (verified 2026 W1: QB mean 30.7→9.6 after carrying `depth_chart_rank`/contracts forward + defaulting health columns). (5) **In-serving background poller** (mirrors `model_sync.start_refresh_poller`), default 3h, started in `gunicorn.conf.py::on_starting`; its first iteration primes the artifact while workers return `503 warming`.

**Rejected.** (a) *nflverse for the live slate* — it lags; the user requirement is a direct live API. (b) *A separate odds-only API + nflverse for the rest* — only solves the single most-volatile input and still rides the nflverse cadence for rosters/injuries. (c) *Computing predictions in a scheduled CI job* (artifact-upload, like refresh-splits) — kept as the documented fallback if the in-serving `build_features` (≈ minutes on warm caches, Risk #2) proves too heavy; the in-serving poller was chosen for simplicity + freshness. (d) *Recomputing only the new rows* — `build_features`' cross-player/season groupbys need the full frame; deferred as a perf optimization.

**Consequence.** Serving-only → triggers `deploy.yml`, **no model retrain**. The deployed container already syncs `data/raw/*` (so `load_raw_data` runs off warm caches). **Deploy sizing (learned the hard way):** the first deploy *rolled back* — not from memory (8GB was ample) but from **CPU starvation**: the poller's `_ensure_base_data` (incl. K's slow PBP reconstruction) ran in the gunicorn master concurrently with the 2 workers' own warm-up on a **2-vCPU** task, so the workers couldn't answer ELB `/health` in time and the deployment circuit breaker reverted to the prior image. Fix: the ECS Fargate serving task is **4 vCPU / 8GB** (`infra/aws/task-definition.json` + live revision 451) — the workers keep their proven ~2-vCPU warm-up baseline while the master build uses the other 2. `deploy.yml` also drops the 20-min in-workflow stability wait (`wait-for-service-stability: false`); the circuit breaker still guards prod. The CI-artifact alternative remains the documented fallback if the in-serving build cost ever becomes undesirable. ESPN endpoints are unofficial — a schema drift fails `espn_live.py`'s parsers loudly (fixture-tested), not the whole site, and the poller's broad try/except keeps serving up. K/DST are surfaced as "coming soon" until their synthetic-injection paths land.
